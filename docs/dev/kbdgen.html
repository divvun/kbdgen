This guide is for people changing kbdgen: how the workspace is laid out, how a target build runs, how the code is tested, and how each target’s generator works. DEV.md in the repository is the short version: building, running the tests and regenerating these pages.

The specification in docs/spec/ is normative; where this guide and the spec disagree, the spec wins. The user guide describes the command line and the formats from the outside.

Architecture

kbdgen is one Cargo workspace. The root package is the kbdgen command line tool; crates/ holds the keyboard model, the engine, LDML support and the three host bindings. The specification in docs/spec/ says what all of it must do, and plan/ tracks which parts are done.

The workspace

Crate Kind Holds

kbd-model

no_std library

The keyboard model: a superset of CLDR LDML Keyboard 3.0, stored fully resolved, with its invariants (Keyboard::validate) and its DVKB binary encoding (Keyboard::to_bytes, from_bytes).

kbd-engine

no_std library

The engine. Model::key takes a model, the host’s State, the text before the caret and a key event, and returns the edit to make and the next state. It is deterministic and does no I/O. Every host runs it: the Windows text service, the ChromeOS extension through WebAssembly, the Linux IBus engine, and kbdgen itself when it derives dead-key tables or runs tests.

kbd-ldml

library

LDML keyboard3 XML through xmlem: reading, resolving a document to the model, exporting a model to a document, and writing. Embeds the CLDR import files (crates/kbd-ldml/data/).

kbd-tsf

cdylib

The Windows text service, a TSF text input processor that runs kbd-engine on the model each layout DLL carries. Built for release by kbdgen tsf.

kbd-wasm

cdylib

kbd-engine for WebAssembly hosts, as a C ABI of integers and byte buffers. kbdgen’s build.rs compiles it for wasm32-unknown-unknown and the ChromeOS target embeds the module as engine.wasm.

kbd-ibus

binary and library

The Linux IBus engine, ibus-engine-divvun, which runs kbd-engine on the model of each installed keyboard and speaks IBus’s D-Bus protocol itself, through zbus. Unix only; released separately from keyboards.

kbdgen

binary and library

The command line, bundle loading, the format 4 layout format and its lowering, the format 3 migrator, and the target generators.

The split follows what runs where. Code that ships inside a keyboard (kbd-model, kbd-engine) is no_std and never panics, and the model has nothing whose order or encoding varies by platform (no hash maps, no floating point), so both build for every device triple and behave the same on each. Parsing XML and YAML happens once, at build time, in the std crates. All member crates deny unwrap, expect, panic! and slice indexing outside tests (see their [lints] and clippy.toml), and tests/workspace.rs checks each crate’s dependencies against docs/spec/ldml/crate.md.

default-members leaves out kbd-tsf, kbd-wasm and kbd-ibus, so a plain cargo build or cargo test skips them; use --workspace to include them.

The kbdgen crate

src/main.rs

The clap command line. It sets up logging, loads the bundle and dispatches to a target build or an ldml command.

src/bundle/

read_kbdgen_bundle loads a bundle into a KbdgenBundle: the project, the format 3 layouts (parsed into the types in src/bundle/layout/), the paths of the format 4 layouts, the target files and the resources. reject_v4_layouts decides which targets accept format 4 layouts. fetch.rs is kbdgen fetch.

src/ldml/

Everything about layouts as keyboards: yaml/ is format 4 (loading, lowering to keyboard3 documents, and import from them), migrate/ converts format 3 to format 4, conformance/ runs test vectors, and cli.rs, export.rs, import.rs and compile.rs implement kbdgen ldml.

src/build/

The target generators, one module per target, and the BuildStep and BuildSteps traits in mod.rs. windows/kbdl/ generates and builds the layout DLLs; windows/tsf/ is kbdgen tsf. linux/ writes the XKB layouts (linux/xkb/), the IBus engine’s data (linux/ibus/) and the on-screen keyboard layouts (linux/osk/). migration.rs migrates format 3 layouts in memory for the ChromeOS and Linux targets, and output.rs and diag.rs are shared by several targets.

src/yaml.rs

Every YAML text kbdgen reads or writes goes through it, so all follow one set of rules: YAML 1.2 scalars (no, y and 0755 are strings), no duplicate keys, no tags YAML does not define, << an ordinary key, and one document per text. It is built on serde-saphyr. tree reads a text as a serde_json::Value with string keys, which format 4 loading checks itself and from_tree reads as a type; from_str reads straight into a type, any scalar into a string field; to_string writes. An Error gives the path to the problem and its line and column on one line.

build.rs

Builds kbd-wasm for WebAssembly in a nested cargo with its own target directory, and leaves kbd_wasm.wasm in OUT_DIR for the ChromeOS target to include_bytes!. For a Linux target it also asks pkg-config for xkbcommon and xkbregistry, and sets the cfg kbdgen_xkbcommon when it finds both, so the libxkbcommon test links them (Tests).

examples/

Developer tools: migrate-survey migrates every layout of the given bundles in memory and reports the defects; pbxproj-roundtrip reads an Xcode project.pbxproj and prints it as kbdgen writes it. Run them with cargo run --example <name> -- <arguments>.

From a layout to the engine

A format 4 layout reaches the engine in three stages:

  1. src/ldml/yaml loads the YAML strictly and lowers it to one LDML keyboard3 document per host (windows, macOS, chromeOS, and so on).

  2. kbd_ldml::resolve turns each document into a kbd_model::Keyboard.

  3. Keyboard::to_bytes encodes it as a .dvkb model, which kbd_engine::Model::from_bytes loads.

LDML XML from kbdgen ldml import enters at the second stage.

Format 3 layouts reach the model through src/ldml/migrate. migrate_bundle_layout converts a layout file to format 4 text in memory, writing nothing, and the text then takes the format 4 path. This is how the Windows DLLs, the ChromeOS extension and the Linux target get an engine model for a format 3 layout. When the migration is blocked by a defect, Windows builds the DLL without a model and warns; the text service then stays inactive for that layout. ChromeOS and Linux stop with an error.

How a target build runs

kbdgen target loads the bundle, checks reject_v4_layouts, creates the output directory, and then runs a list of build steps. A step implements BuildStep, whose only inputs are the loaded bundle and the output path; a target’s BuildSteps lists its steps and runs them in order with build_full, stopping at the first error. Subcommands such as macos generate or android clone run one step on its own. The Build system chapter lists each target’s steps and the conventions a step follows.

The specification

docs/spec/ is the normative description of kbdgen:

  • docs/spec/*.md covers the bundle, the format 3 layout, the command line and pipeline, and each target: kbdl.md (Windows layout DLLs), tsf.md (the text service), macos.md, ios.md with pbxproj.md, android.md, chromeos.md and linux.md (with the IBus engine).

  • docs/spec/ldml/*.md covers the model, the engine, LDML XML, format 4, the migration, the adapters from the model to each target, the kbdgen ldml commands and the tests. ldml/overview.md explains how these fit together, and ldml/crate.md the workspace.

Each rule is a block quote that starts with its id:

> [spec:kbdgen:req:ldml.cli.test]
> `test` MUST run every `tests/*.yaml` of the bundle (`ldml.test.bundle`).

The id’s kind is def (a definition), req (a requirement), sem (behaviour), syn (syntax) or thm (a consequence of other rules, such as the struct sizes that follow from the Windows table layout). A +N suffix, as in ldml.yaml.coexistence+2, is the rule’s version, raised whenever its meaning changes.

Code says which rules it implements with a comment carrying the same id, on the item that implements it. A test says which rules it verifies with /test, or /test/golden for a golden-file test:

#[test]

An annotation names the rule version it was checked against. When a rule’s version is raised, every annotation of it is updated once the code has been checked against the new text. .config/nspec/config.styx says where the spec and the code are, and which rules need a golden test.

Planning with nplan

The work is planned with nplan, in the repository:

The work breakdown: a tree of nodes whose ids follow the tree with dots (targets.windows.dll-gen). Each node has a title, a kind (feat, fix and so on), the nodes it depends on, and the spec rules it implements.   • nplan check runs the checks a commit is gated on (see Testing).

Build system

This chapter covers how kbdgen target runs a target’s build, and the conventions every build step follows for logging and errors.

The pipeline

kbdgen target -b <BUNDLE> -o <OUT> <PLATFORM> runs, in src/main.rs:

  1. read_kbdgen_bundle loads the whole bundle. Any error ends the run here, before anything is written.

  2. KbdgenBundle::reject_v4_layouts fails when the bundle has a format 4 layout and the target cannot build one. Windows, macOS, ChromeOS and Linux can; iOS and Android cannot.

  3. The output directory is created with its parents and canonicalised.

  4. The target’s steps run.

The steps implement two traits from src/build/mod.rs:

#[async_trait(?Send)]
pub trait BuildSteps {
    fn new(bundle: KbdgenBundle, output_path: PathBuf) -> Self
    where
        Self: Sized;

    fn steps(&self) -> &[Box<dyn BuildStep>];
    fn bundle(&self) -> &KbdgenBundle;
    fn output_path(&self) -> &Path;

    async fn build_full(&self) -> Result<()> {
        for step in self.steps() {
            step.build(self.bundle(), self.output_path()).await?;
        }

        Ok(())
    }
}

#[async_trait(?Send)]
pub trait BuildStep {
    async fn build(&self, bundle: &KbdgenBundle, output_path: &Path) -> Result<()>;
}

A step’s only inputs are the bundle and the canonical output path. Whatever a later step needs from an earlier one, it finds in the output directory: macos installer packages the .bundle that macos generate left there, and the iOS and Android steps all work in OUT/repo. That is what lets a subcommand run a single step.

build_full awaits each step in turn and stops at the first error. The steps of each target:

Writing a step

  • Compute everything, then write. GenerateKbdl generates every layout crate in memory before writing the first, and GenerateChromeOs and GenerateLinux build every file before they write the first. A bad layout then fails the step without leaving half an output.

  • Check external tools' exit status, and capture their output rather than letting it interleave with kbdgen’s log: log it at trace on success and put stderr into the error on failure (build_layout in src/build/windows/kbdl/build.rs does this for cargo).

  • Gate on the host only where the tool exists on one OS. The macOS installer step in macos build and macOS icon conversion are the only such places; the Windows DLL build runs on any host.

To add a target: add a module under src/build/ with a BuildStep per step and a BuildSteps for the full build; add a TargetCommand variant and its name() in src/main.rs; decide in reject_v4_layouts whether it accepts format 4 layouts; and specify it in docs/spec/.

Logging

kbdgen logs with tracing. main.rs installs a tracing_subscriber formatter that writes to stderr and filters with RUST_LOG, defaulting to info. Stdout is reserved for a command’s results, such as the paths kbdgen tsf prints for signing; use println! only for those. When a child process would write to stdout, capture its output or send it to stderr, as kbdgen tsf does for cargo with .stdout(std::io::stderr()).

The levels are used like this across the targets:

Level For Examples

error

Nothing. A failure is returned as an error, and main prints it.

warn

The output differs from what the bundle asks for, or something in it was ignored or skipped. The user should look.

Ignoring unknown target file …; Skipping the installer: pkgbuild and productbuild only exist on macOS; Windows table entries that cannot be represented and are omitted

info

One line per milestone a user follows.

Reading bundle …; Generating the Windows layout crates; Building kbdse-NO for x64; Running pod install in …

debug

Per-file and per-command detail.

Wrote …; Running …; Skipping layout se: it has no macOS layers

trace

Bulky raw output.

cargo, rust-lld and gradlew output; the generated distribution.xml

Messages name what they are about (the layout, the file, the variant) and print paths with display(), not {:?}. The Windows, macOS, ChromeOS and Linux generators collect each layout’s warnings and notes in a Diagnostics value (src/build/diag.rs), which logs each one with the layout’s name and also keeps it, so the golden tests can pin them. A Diagnostics is made for one Platform, and logs under that target’s module (kbdgen::build::macos), which the formatter prints before the message, so a warning says which target raised it.

Loading a format 4 layout file (ldml::yaml::load) logs the layout’s own warnings, such as a dead key no \d{} token uses, under kbdgen::ldml::yaml. A command may load one layout several times, as the Windows target’s two steps do, so load logs each warning once per process. ldml migrate loads what it writes with load_value, which logs nothing: it turns the warnings into defects.

Errors

Build steps and main return anyhow::Result. Modules whose callers need to tell errors apart define them with thiserror: bundle::Error, ldml::LdmlError and ldml::compile::CompileError in kbdgen, and the error types of kbd-ldml and kbd-engine. main returns the error, and anyhow prints it with its chain of causes.

The house style, as in src/build/windows/kbdl/build.rs:

let crate_dir = dunce::canonicalize(&crate_dir)
    .with_context(|| format!("{name}: crate directory {} is missing", crate_dir.display()))?;
for variant in &VARIANTS {
    tracing::info!("Building {name} for {}", variant.name);
    let output = cargo_command(&crate_dir, name, variant)
        .output()
        .with_context(|| format!("{name} ({}): cargo could not be started", variant.name))?;
    let stderr = String::from_utf8_lossy(&output.stderr);
    if !output.status.success() {
        bail!(
            "{name} ({}): cargo failed with {}:\n{}",
            variant.name,
            output.status,
            stderr.trim_end()
        );
    }
    // ...
    std::fs::write(&target, &bytes).with_context(|| format!("write {}", target.display()))?;
}

  • Every I/O error gets context naming the path: write {path}, create {path}, read {path}. The context is the action and its object, not "failed to …"; the cause already says what went wrong.

  • Messages start lower case, have no full stop, and lead with the subject: the layout, the variant, or the file (kbdse-NO (x64): cargo failed …).

  • When the fix is known, the message gives it: install it with rustup target add …, run the macOS generate step first, pass --force to replace it.

  • A tool that cannot be started says what to install (`xcodebuild` could not be started; install Xcode). A tool that fails gives its command, its exit status and its stderr.

  • Nothing a bundle or the environment can cause may panic. expect is for invariants the code itself guarantees, and its message states the invariant (read_kbdgen_bundle only accepts bundles with a UTF-8 stem).

Testing

Running the tests

The tests run with cargo-nextest:

cargo install cargo-nextest --locked
cargo nextest run --workspace

--workspace is needed: kbd-tsf, kbd-wasm and kbd-ibus are not default members, so without it their tests do not run. To run some tests only, pass a filter: cargo nextest run --workspace keylayout.

Most tests sit next to the code, in #[cfg(test)] modules. The others:

  • tests/ldml_cli.rs runs the kbdgen binary (ldml commands, and target builds of format 4 layouts) and checks exit status and output files.

  • tests/workspace.rs checks each crate’s dependencies against docs/spec/ldml/crate.md.

  • tests/ldml_kmc.rs validates exported LDML with Keyman’s kmc.

  • crates/kbd-engine/tests/targets.rs builds kbd-model and kbd-engine for every device triple.

  • crates/kbd-tsf/tests/ holds the text service tests: self_contained.rs runs everywhere, vm.rs and acceptance.rs only on Windows.

  • crates/kbd-ibus/tests/ holds the IBus engine tests: ibus.rs needs ibus-daemon, and the others run everywhere (Tests).

Ignored tests

Tests that need extra tools or a particular machine are marked #[ignore], with a reason. --run-ignored all adds them to a run, and --run-ignored only with a filter runs one:

When a change to a generator is intended, regenerate the files with KBDGEN_BLESS set. Each golden test then writes its current output over its file before comparing, so the run passes and git diff shows exactly what changed:

KBDGEN_BLESS=1 cargo nextest run --workspace

kbdtables.txt comes from built DLLs, in an ignored test, so rewriting it needs that test too:

KBDGEN_BLESS=1 cargo nextest run --workspace --run-ignored only -E 'test(fixture_dlls_hold_their_golden_tables)'

Read the diff before committing it. A failing golden test prints which file differs and where; a missing file asks for KBDGEN_BLESS=1 to create it.

The DLL bytes themselves are not golden: code generation changes with the Rust release, while the decoded tables do not.

Test vectors

The engine is tested with typing vectors in the format of a bundle’s tests/*.yaml (described in the user guide). kbdgen’s own are in crates/kbd-engine/tests/golden/: layouts in layouts/ and v3/, LDML keyboards in keyboards/, and the vectors in tests/. src/ldml/conformance/tests/ runs them, together with the CLDR 48 keyboards and keyboardTest3 vectors vendored in crates/kbd-ldml/testdata/cldr/48/. These files are inputs written by hand, not output, so KBDGEN_BLESS does not touch them. Add a vector file to tests/ to cover a new engine behaviour.

The same directory has the round-trip tests (roundtrip.rs: XML, the model, format 4 YAML and the binary model, each written, read back and written again) and the property tests (robust.rs: decoding arbitrary bytes and typing arbitrary keys never panic).

Differential tests

The Windows, macOS, ChromeOS and Linux generators each have a test that types on what the generator wrote and on kbd-engine with the same model, and requires the same text. Windows, macOS and Linux keep a list of the differences their native formats cannot avoid (exceptions.rs in each differential/ directory); a difference must match an entry there, and any other fails the test. ChromeOS runs the engine itself, so it allows none.

Windows (src/build/windows/kbdl/differential/)

Simulates ToUnicodeEx on the generated KBDTABLES: every layer at each of the 49 ISO positions and the space bar, then every dead-key path. Runs on every host. On Windows, windows.rs also loads the built DLLs and checks the real ToUnicodeEx against both (ignored; see above).

macOS (src/build/macos/differential/)

Reads the written .keylayout back and simulates it. Runs on every host; nothing calls macOS. It also checks a format 3 layout’s .keylayout against the one built from its migration.

ChromeOS (src/build/chromeos/differential/)

Generates the extension, then harness/typing_test.ts loads its background.js, engine.wasm and models in Deno, behind a fake chrome.input.ime and text field, and types every case. This needs Deno: deno on PATH, or its path in DENO. Without it, the test prints that it is skipping and passes, so check its output when you change the ChromeOS target.

Linux (src/build/linux/xkb/differential/)

Reads each written XKB symbols file back and simulates it as libxkbcommon and IBus’s simple engine type it: every written key in all eight states of Shift, Caps Lock and AltGr, then every dead-key path of up to three keys. Runs on every host. On Linux with libxkbcommon, xkbcommon.rs also compiles and types the layouts through the real library (see above). The IBus engine runs the engine itself; its planner is tested against a fake client in crates/kbd-ibus/tests/planner.rs.

The migration is checked the same way: src/ldml/migrate runs each migrated layout through the engine against what the format 3 platforms typed, and reports every difference as a defect.

Windows text service tests

The text service only runs inside Windows, so its end-to-end tests run on a Windows 11 machine (a VM is fine) with a user signed in at the desktop. They type with SendInput and switch input methods, so they take over the desktop while they run.

The VM test (crates/kbd-tsf/tests/vm.rs, with the scripts in crates/kbd-tsf/tests/vm/) builds the text service under a test CLSID, checks that registration refuses misnamed and misplaced DLLs, registers the fixture layouts, types each case into Win32, RichEdit, WPF and console windows in 32- and 64-bit processes, and removes everything again. Run it elevated, for example over SSH, while the same user is signed in:

kbdgen target -b crates/kbd-tsf/tests/vm/fixture.kbdgen -o C:\kbd-vm windows
set KBD_TSF_VM_LAYOUT=C:\kbd-vm
cargo test -p kbd-tsf --test vm -- --ignored --nocapture

The acceptance test (crates/kbd-tsf/tests/acceptance.rs) installs the keyboard as a user gets it, with Inno Setup 6 and kbdi, types each case through the installed text service, and uninstalls it. Its file header lists the setup and the variables KBD_TSF_ACCEPTANCE_ISS and KBD_TSF_ACCEPTANCE_KBDI.

Checks before committing

nplan check runs the checks a commit is gated on, as configured in .config/nplan/config.styx:

Check Command

format

cargo fmt --all -- --check

lint

cargo clippy --workspace --all-targets

Targets

One chapter per target generator under src/build/: what it reads, the steps it runs, and how it is tested.

Windows

The Windows target has two parts:

  • the layout DLL generator, src/build/windows/kbdl, which kbdgen target … windows runs. It writes a no_std Rust crate per layout and builds it into a keyboard layout DLL for x86, x64, arm64 and WOW64. The DLL is specified in docs/spec/kbdl.md (rules kbdl.), and the derivation of its input from a v4 layout in docs/spec/ldml/kbdl.md (ldml.kbdl.).

  • the text service, the crate crates/kbd-tsf: a TSF text input processor that runs kbd-engine on the compiled keyboard each layout DLL carries. kbdgen tsf builds it, from src/build/windows/tsf. It is specified in docs/spec/tsf.md (tsf.*).

The specs are normative and exhaustive; this chapter is a map of the code. Code cites the rules it implements as [spec:kbdgen:req:kbdl.build] and the tests that verify them as [spec:kbdgen:req:kbdl.build/test], so searching for a rule id finds both.

Layout DLL generator

Pipeline

WindowsBuild in src/build/windows/mod.rs runs two build steps, both in kbdl/mod.rs:

  1. GenerateKbdl calls generate_bundle, which, for each layout with Windows output in bundle layout order, derives the generator input and the encoded engine model (source_layout), then generates the crate files (generate). Any error fails the whole bundle before anything is written. write then puts each crate in <out>/build/<name>/, removing stale files but keeping cargo’s target and target-wow64.

  2. BuildKbdl lists the crates again with layout_names, which for v4 layouts only loads, lowers and resolves. No diagnostic is reported twice: the adapter does not run, and ldml::yaml::load logs a layout’s load warnings once per process. It checks the toolchain once, then builds every crate for every variant.

generate is the core, and does no I/O:

pub fn generate(
    input: &LayoutInput,
    model: Option<&[u8]>,
    diag: &mut Diagnostics,
) -> Result<GeneratedLayout> {
    check_metadata(&input.metadata)?;
    let tables = tables::build(input, diag)?;
    let version = resources::file_version(&input.metadata, diag);
    Ok(GeneratedLayout {
        name: input.metadata.name.clone(),
        cargo_toml: source::cargo_toml(&input.metadata.name),
        lib_rs: source::lib_rs(&tables),
        res: resources::res_file(&input.metadata, version, model),
    })
}

Warnings and information go through crate::build::diag::Diagnostics, made for Platform::Windows, which logs each message under kbdgen::build::windows with the keyboard name as it is raised and keeps it, so tests and golden files can see what was reported. Fatal conditions are returned as errors.

Input

input.rs defines LayoutInput, the format-independent input of kbdl.input: metadata, the decimal separator, a value or "no key" per Layer at each of the 49 positions E00…B11, up to three extra modifiers, the dead-key tree (DeadKeyNode, a leaf or a branch whose " " child is the standalone output), dead-key names, key-name overrides, and the Shift Lock and LRM/RLM flags. Two producers fill it.

v3 layouts (bundle.rs, kbdl.input.bundle) read the layout’s windows section and its transforms. v3 cannot express extra modifiers, names, flags or B11, so those stay empty. The engine model of a v3 layout comes from v3_model in mod.rs: the layout file is migrated in memory (ldml::migrate) and its windows keyboard encoded. When the migration fails, is blocked or has no windows keyboard, the DLL is built without the model and a warning says why (ldml.kbdl.model-resource).

v4 layouts (adapter/, ldml.kbdl.*) start from the compiled model. adapter::load lowers the layout’s host documents and compiles the windows one; adapter::adapt then derives the input:

  • layers.rs gives each kbdl layer the engine’s modifier state for it (layer_states) and takes the hardware layer the engine would select, then the key at each position by scan code and its value. kbd-engine exposes no layer-selection API, so this repeats the engine’s selection; a test checks that the two agree.

  • dead_tree.rs builds each dead key’s tree by running kbd-engine: press the dead key, then each distinct value of the layers, and record what is committed or left pending (ldml.kbdl.dead-tree). The DLL’s dead keys therefore compose as the engine does wherever the tables can.

  • classify.rs reports, once per layout, what only the text service provides (ldml.kbdl.classify).

  • windows_inputs in adapter/mod.rs copies the Windows-only options of the model: extra modifiers, the flags, dead-key names, key names and the decimal separator.

The model the DLL embeds is the encoding of the same compiled layout, so the DLL and the text service derive from one source. Metadata comes from bundle::metadata for both formats (kbdl.metadata.bundle, kbdl.metadata.locale): the keyboard name kbd<id> or kbd and the first five characters of the tag, the display name for the primary language subtag, the LCID from iso639::lcid and the tag, the project’s organisation and copyright, and the Windows target’s version and build.

Tables

tables::build computes Tables, the contents of the KBDTABLES of kbd.h, from the input:

  • the modifier bindings and character-table columns (kbdl.layers, kbdl.modifiers), with up to three extra modifiers bound to spare virtual keys

  • one character row per position, with Caps Lock attributes, the SGCAPS rows and the dead rows that follow them (kbdl.vk-chars, kbdl.caps)

  • dead keys: the dead id of each dead state, one aDeadKey group per state, and chained states, falling back to Private Use units downward from U+F8FF (kbdl.dead-keys*)

  • ligatures of 2 to 16 UTF-16 units (kbdl.ligatures)

  • the scan-code maps, with the keys of extra modifiers rebound (kbdl.scancodes*), key names with overrides, and the locale flags

Most warnings come from here. build ends with check_invariants (kbdl.tables.invariants), so a generator bug fails generation instead of producing a DLL that Windows misreads.

Source

source.rs writes Cargo.toml and lib.rs (kbdl.crate, kbdl.source). lib.rs is ASCII and byte-for-byte deterministic: every piece of layout text is written as hexadecimal UTF-16 literals (kbdl.escaping). It holds:

  • the kbd.h structures as #[repr(C)] types, with variable-length members as const-generic arrays (kbdl.structs)

  • a pointer slot P<T>, which under the wow64 feature is a 32-bit pointer padded to 8 bytes, so a 32-bit build has the 64-bit table layout that WOW64 needs (kbdl.structs.pointers, kbdl.wow64)

  • const assertions of every size and offset, so a layout mismatch fails compilation (kbdl.structs.layout)

  • the tables as immutable statics, and the one export, KbdLayerDescriptor (kbdl.export)

There is no .def file: rust-lld ignores a /DEF given after rustc’s own, and rustc already exports KbdLayerDescriptor under that name on every target.

Resources

resources.rs writes <name>.res directly, without rc.exe (kbdl.resources*). It holds an empty entry, the RT_VERSION resource, the engine model as RT_RCDATA 1 when the layout has one (tsf.data.resource), and string table blocks with strings 1000 (description) and 1100 (language name) under the layout’s LCID, and 1200 (locale name) under 0x0409. The bytes are what rc.exe writes for the equivalent script. file_version turns the target’s version and build into a.b.c.d.

The merges put code and data in one read-execute .data section, because Windows 11’s LoadKeyboardLayout rejects a layout DLL whose code and data lie in separate sections (kbdl.image). /NODEFAULTLIB drops msvcrt.lib, which non-Windows hosts lack, so the build needs no MSVC on any host. The DLL is then copied to <out>/<variant>/<name>.dll.

Tests

Run the generator’s tests with:

cargo test --lib build::windows::kbdl

Golden tests (kbdl/golden/) generate four fixtures and compare their Cargo.toml, lib.rs, .res and diagnostics with files under kbdl/testdata/golden/<fixture>/:

  • vro - the v4 Võro layout, crates/kbd-engine/tests/golden/layouts/vro.yaml

  • vro-v3 and se-NO-v3 - the v3 layouts of crates/kbd-engine/tests/golden/v3/, whose tables come from kbdl.input.bundle and models from migration

  • features - kbdl/testdata/features.yaml, a v4 layout with chained and named dead keys, ligatures, an extra modifier, SGCAPS, the 49th key, Shift Lock, LRM/RLM, a decimal separator and key-name overrides

fixture_dlls_hold_their_golden_tables is ignored by default because it needs the three Windows targets. It runs both build steps on each fixture, verifies every variant’s image, and decodes the KBDTABLES that KbdLayerDescriptor returns by following every pointer (golden/kbdtables.rs), comparing the result with kbdtables.txt. The DLL bytes are not golden: they are reproducible for one toolchain, but code generation changes between Rust releases, while the decoded tables do not.

cargo test --lib build::windows::kbdl::golden -- --include-ignored
KBDGEN_BLESS=1 cargo test --lib build::windows::kbdl::golden -- --include-ignored

The second command rewrites the golden files; review the diff.

Differential tests (kbdl/differential/, tsf.test.differential) check that the DLL types what the text service types. For every fixture layout (the v4 and v3 golden layouts of kbd-engine and kbdl/testdata/vro-v3.yaml) they compare kbd-engine, on the model embedded in the generated .res, with simulate::Dll, which applies the generated tables as ToUnicodeEx does. The cases are every layer at each of the 49 positions and the space bar, then every dead-key path up to four keys. Each difference must be one of the exceptions listed in exceptions.rs, each documented in the spec, such as Caps+Shift on CAPLOK keys or multi-unit dead-key outputs. each_listed_exception_explains_a_difference and corrupted_tables_are_not_explained keep that list honest. The same module checks that every built .res decodes to the layout’s model (tsf.test.engine) and how embedded model versions load (tsf.data.version).

On Windows, differential/windows.rs checks the simulation against the real ToUnicodeEx: it installs each fixture’s DLL under a test KLID (a0f00409 upwards, as kbdzf<n>.dll in System32), types every case, and removes them again. Run it elevated, in an interactive session:

cargo test real_dlls -- --ignored

Adapter tests (adapter/tests/) check each ldml.kbdl.* rule on small layouts, the embedded model, and the v4 Võro layout against its v3 counterpart through the tables both produce. migrated.rs compares a v3 layout’s DLL with the DLL of its migration; the migration tests in src/ldml/migrate/tests use it to split the differences into those the migration’s defects explain and the rest.

Text service

Crate structure

crates/kbd-tsf builds kbd_tsf.dll, a cdylib with windows and windows-core 0.62. Everything that needs no TSF call is in host-independent modules, tested on every host; src/win/, compiled only on Windows, adapts TSF and ETW to them.

COM entry points

The DLL exports exactly DllGetClassObject, DllCanUnloadNow, DllRegisterServer and DllUnregisterServer (tsf.component.crate). DllGetClassObject serves only the CLSID {5E668C8A-2FB8-41D2-90B1-9C132653FA9D}. Building with KBD_TSF_CLSID set to another GUID compiles that one in instead, which the Windows tests use to register a build beside an installed text service. build.rs silences the linker’s LNK4104 warning about the exports.

The Tip object (win/tip.rs) implements ITfTextInputProcessorEx and the sinks of tsf.component.interfaces: thread manager events, key events, text edits, compositions, compartments, the display attribute provider and language profile switches. Every Divvun keyboard is a profile of this one CLSID, so switching between them does not reactivate it; the profile sink loads the new profile’s keyboard data instead.

Keyboard data and the engine

On activation and on each profile switch, win/data.rs looks under HKLM\SYSTEM\CurrentControlSet\Control\Keyboard Layouts for the layout whose Layout Product Code is the profile GUID, loads its Layout File from System32 as a resource-only image, and decodes RT_RCDATA 1 with Model::from_bytes (tsf.data.locate). Results are cached per process. A profile whose data cannot be loaded is inert: it eats no keys, and keeps the locate::Reason for diagnostics (tsf.data.inert).

Each context has a Document with one engine State. For each key, Model::key(&State, &Context, &KeyEvent) gives an Action, and the planner turns it into text operations:

  • in a context whose text can be read, a SetText over the range before the caret, inside a read-write edit session (tsf.edit.apply)

  • in a transitory context, such as a Win32 EDIT, which returns no text before the caret: insertions with SetText at the selection, and edits that delete with one SendInput of Backspaces and Unicode characters. The engine’s context is then a cache of what the text service typed (tsf.edit.inject, tsf.edit.cache).

  • a non-empty preedit as a TSF composition, in contexts whose text can be read (tsf.edit.preedit)

TSF calls OnKeyDown only for keys OnTestKeyDown ate, so OnTestKeyDown decides every key in a read-only synchronous session, without changing engine state, and OnKeyDown applies the kept decision (tsf.keys.phases). The engine is pure, so that decision is exact. TSF calls no key sink while Alt is held, so AltGr and Ctrl+Alt chords arrive as preserved keys (tsf.keys.preserved). The engine is reset whenever the document changes in a way the text service did not cause (tsf.edit.reset).

Registration

DllRegisterServer writes the CLSID’s InprocServer32 and the TSF categories; profiles are registered by kbdi, not the text service (tsf.register.server). registration.rs decides first and win/facts.rs gathers what it decides on. Registration refuses, writing nothing, unless the DLL is named as kbdgen tsf names it, lies in a directory named for its own kbd-tsf version under the 64-bit %ProgramFiles%, and every file the registration loads grants read and execute to ALL APPLICATION PACKAGES and ALL RESTRICTED APPLICATION PACKAGES (tsf.arch.registration, tsf.register.upgrade, tsf.security.appcontainer). To register a local build, copy it to %ProgramFiles%\Divvun\Text Service\<version> first.

Diagnostics

The text service records no typed text, context text or key identities (tsf.component.logging). Its only output is ETW TraceLogging events from the provider Divvun.Keyboard.TextService ({B7732613-C499-504F-2AB7-FF5A4E513A9B}), listed in tsf.component.events; the user guide shows how to collect them.

  • diag::Event is Copy + 'static, checked at compile time, so no event can hold a string read at run time.

  • A per-thread gate drops every event on a thread where the text service is not activated, or is activated in secure or immersive mode. Only the registration exports are exempt.

  • etw.rs encodes events as TraceLoggingProvider.h defines them. win/trace.rs registers the provider only while it writes one event, with no enable callback: the DLL has no DllMain and COM may unload it without asking DllCanUnloadNow, so a longer registration would outlive it. Microsoft’s tracelogging crate is not used because it links OneCore_apiset.lib.

tests/self_contained.rs scans the sources for anything that talks to other processes, the network or files, starts processes, writes the registry outside registration, creates windows, or logs other than through the gate (tsf.component.self-contained).

Panic containment

TSF loads the text service into every process the user types in, and an unwind that reaches an extern "system" function aborts the process. Every export and COM method therefore runs its body through guard::contain, which turns a panic into E_UNEXPECTED, writes a Panicked event with the panic’s location but never its message, and poisons the text service for the process: from then on it passes every key and requests no edit session (tsf.component.panic). This needs panic = "unwind", the release default, which the workspace keeps.

Building

kbdgen tsf -w <workspace> -o <out> (src/build/windows/tsf/mod.rs) runs the toolchain check of the layout build, then for each of i686-pc-windows-msvc, x86_64-pc-windows-msvc and aarch64-pc-windows-msvc:

cargo rustc --package kbd-tsf --release --lib --target <triple> \
  --target-dir <workspace>/target -- -C target-feature=+crt-static

The C runtime is linked statically, because the text service loads into processes on machines without the Visual C++ runtime. The DLL links std, which needs MSVC and the Windows SDK, so this runs on Windows. verify::verify_tip checks each DLL’s machine, the DLL flag, exactly the four exports with none forwarded, and no C runtime among its imports; the DLL is renamed divvun_tip_x86.dll, divvun_tip_x64.dll or divvun_tip_arm64.dll.

For Windows on Arm, divvun_tip.dll is an Arm64X pure forwarder whose native exports forward to divvun_tip_arm64 and whose x64 exports forward to divvun_tip_x64 (tsf.arch.arm64x). A merged Arm64X Rust DLL crashes in x64 processes (rust-lang/rust#145154). coff.rs writes the native and Arm64EC load configuration objects, with the data of LLD’s own test inputs, so no C compiler or assembler is needed; link_forwarder links them with rust-lld -flavor link -machine:arm64x and two generated .def files, and verify::verify_forwarder checks both views. This part runs on any host, and so do its tests:

cargo test --lib build::windows::tsf

write_release writes the four files only when all have passed, and kbdgen tsf prints their paths to stdout for signing (tsf.security.signing).

Tests

kbd-tsf is not a default workspace member, so name it:

On every host this runs the unit tests in src/tests/ against a fixture keyboard (tests/fixture.rs) and an in-memory context (tests/fake.rs): key identity, AltGr, extra modifiers, Shift Lock, edits, preedits, the cache, resets and registration decisions (tsf.test.host). macOS

The macOS target writes one Apple .keylayout per layout into a keyboard-layout bundle, and can package the bundle as a .pkg. Layouts come from two places: the macOS section of a v3 layout, and the macOS keyboard of a compiled v4 layout. Both are turned into the same plain-data keylayout input, and one writer turns that into XML. So v3 output stays exactly as it was, and the two paths can be compared document by document.

The rules live in two spec files:

  • docs/spec/macos.md: the document, key maps, dead keys and transforms as the v3 path writes them (keylayout.*), and the bundle and installer (macbundle.*);

  • docs/spec/ldml/macos.md: the keylayout input, the v4 adapter, what it reports, and the tests (ldml.macos.*), including three open questions.

Every document is generated in memory before MacOsBundle::new creates a directory, so a layout that fails writes nothing. generate_bundle also rejects two layouts with one keyboard name.

The keylayout input

KeylayoutInput is one document in emission order: the keyboard name, tag and display names, the default map index, the key maps and the terminators. A KeyMap holds the keys attributes of its <modifier> elements and its keys in order. A Key is a key code with a Binding: Output(text), or Action { id, whens }. A When has a state and an output, a next state, or both. All texts are already decoded; the writer copies them.

A map with no modifier terms is only reachable as the default index, and the writer gives it no <keyMapSelect> (the DTD requires one <modifier> in each). v3 never produces one; the adapter does for an other layer.

The v3 path

v3::layout_input returns None without a macOS section. Otherwise:

  1. initialize_key_transition_map splits each layer into tokens, requires 48, and assigns them to MACOS_KEYS in ISO order. Transitions are kept per layer in an IndexMap from the raw token to its positions, which is what groups the <key> elements by token, in order of first occurrence (keylayout.keymaps.tokens).

  2. Only when the layout has transforms and macOS.deadKeys has an entry for one of its layers:

    1. register_dead_keys makes every top-level transform a dead_keyNNN state, with its ' ' child as the terminator;

    2. process_transforms turns each matching position on a layer with a deadKeys entry into an action with a none output plus one when per dead key;

    3. create_dead_key_actions replaces each dead-key token with an action whose only when is none → next.

  3. key_maps adds the fixed keys, code 65 with decimal, and code 49 with a space, and takes each map’s term from layers::layer_attributes.

Action ids come from one counter as the steps run, so replaced actions leave gaps; that is part of the specified output. Behaviours the spec pins and the tests keep: macOS.space is ignored, \u{0} is an ordinary output, a dead-key token repeated on one layer ends up at the last position only (keylayout.actions.dead-key-next), and a nested transform panics (layout.transforms.dead-key-entries).

The v4 adapter

adapter::load lowers the layout’s file (ldml::layouts::host_documents) and returns None when no document is for the macOS host, which happens when the layout has neither a hardware.macOS nor a hardware.default variant. Otherwise it compiles the layout (compiled_layouts).

adapter::adapt takes the macOS keyboard of the compiled layout:

  1. layers::derive makes one MapPlan per hardware layer macOS can select. selectable_sets drops sets with an extra modifier, and caps sets when Caps Lock is bound as an extra modifier, and warns about sided sets. Each plan has a cell for each of the 48 ISO positions that types something, located by scan code through the Windows KBDL tables (POSITION_NAMES, POSITION_KEYS) and coded through MACOS_KEYS, plus the space bar at scan code 39. Each distinct value, text or a single dead-key marker, is interned in Derived::values with the first key press that gives it, which the dead-key probe reuses.

  2. modifiers::terms writes each layer’s terms. A set that a v3 layer migrates to gets that layer’s v3 term, so migrated layouts keep their modifier maps; others get a term built from their components, with command? on typing sets.

  3. dead_keys::derive loads the keyboard into kbd_engine (Nfc, CancelOrPass, host MacOs). Pressing each dead key from the reset state must commit nothing and leave exactly its marker pending, else the layout fails. From each state it presses every value and compares the result with what the .keylayout would do by default: type the terminator, then the value. A difference becomes a when; a result that leaves a single marker and commits nothing becomes next, and a state found that way is probed too, which is how chained dead keys appear. Anything else is omitted with a warning. States are numbered in deadKeys order.

  4. classify::classify counts what the .keylayout cannot express, and classify::report turns that into one warning per feature, or the single information message.

  5. key_map assembles each map: the cells grouped by value, the fixed keys, the decimal key and the space bar. A value with when elements, or a dead key, is an action, numbered in emission order.

Warnings go to a Diagnostics for Platform::MacOs (crate::build::diag), the type the Windows KBDL adapter, ChromeOS and Linux also use. It logs each message through tracing as it is recorded, under kbdgen::build::macos, and keeps them for the tests. generate_bundle only keeps Adapted::input. The adapter also reuses starts_with_marker and is_generated_backspace from the Windows adapter.

Writer, bundle and installer

writer::write parses the embedded template with xmlem, sets the keyboard’s id (util::keyboard_id) and name, appends each map and its actions, removes <actions> when empty (macOS refuses an empty one), adds <terminators> when there is a state, and prints with two-space indent in hex entity mode.

MacOsBundle serializes Info.plist with the plist crate; KLInfo_* entries are a flattened IndexMap, so they follow the CFBundle* keys in the order layouts were added. InfoPlist.strings lines use Rust Debug quoting, not Apple’s escaping. Icons are converted with convert and iconutil in a temporary .iconset directory, on macOS hosts only.

GenerateInstaller checks that the bundle exists, runs pkgbuild into a temporary directory, writes distribution.xml there with xmlem, and runs productbuild into <out>/<bundleId>.pkg. Every external tool goes through util::run, which keeps the tool’s output off kbdgen’s stdout and puts its stderr in the error.

iOS

The iOS target does not write an app of its own. It clones the giellakbd-ios template, writes the keyboards' data into it, rewrites the template’s Xcode project and plists, and drives fastlane, CocoaPods and xcodebuild to sign, archive and export the app. Only v3 layouts are read: KbdgenBundle::reject_v4_layouts stops every ios command when the bundle has a v4 layout.

The pbxproj model

Pbxproj::from_path copies the project to a temporary tmp.pbxproj, runs plutil -convert json on the copy, and deserializes the JSON into Pbxproj: the top-level fields and objects, a BTreeMap from ObjectId to Object, an enum tagged by isa with one variant per modelled kind (pbxproj.model lists the 18). The structs reject unknown fields, except the build phases, so a template that starts using a new field fails loudly instead of losing it. Reading needs plutil, so it only works on macOS.

Reading normalizes order: objects by id, and id lists as sorted sets (BTreeSet, pbxproj.model.ordering). buildSettings is an IndexMap in the order plutil produced, which need not be the file’s.

serialize_pbxproj.rs writes the model back in the old-style plist format Xcode uses: a section per kind, even when empty, objects in id order, and fixed quoting rules per field (pbxproj.serialize, pbxproj.quoting). kbdgen does not know object names, so most comments are the placeholder TODO; Xcode ignores comments when reading and rewrites them when it next saves the project.

New objects get random 24-character hex ids (ObjectId::new_random). The example pbxproj-roundtrip reads a project and prints it re-serialized, which is the quickest way to check the model against a new template:

cargo run --example pbxproj-roundtrip -- repo/GiellaKeyboard.xcodeproj/project.pbxproj

Build chain

IosBuild::new lists the steps:

  1. CloneGiellaKbd: git clone https://github.com/divvun/giellakbd-ios.git repo in the output directory. It fails when repo exists.

  2. GenerateIos, then GenerateXcode, as above. Neither checks for targets/ios.yaml up front; without it GenerateXcode only renders the icons, and the next step fails.

  3. FastlaneProvisioning: requires appStoreKeyJson and teamId. For every id of all_pkg_ids it spawns fastlane match appstore and fastlane sigh (writing <id>.mobileprovision) as independent tokio tasks, at most 12 running at once (a Semaphore), all in repo, and awaits them in spawn order. embed_profiles then decodes each profile with security cms -D -i, sets PROVISIONING_PROFILE and PROVISIONING_PROFILE_SPECIFIER on its target (re-reading and rewriting the project), and writes repo/opts.plist for the export.

  4. PodInstall: pod install --repo-update --project-directory=<repo>.

  5. BuildXcarchive: requires teamId and codeSignId. xcodebuild archive with the workspace GiellaKeyboard.xcworkspace, scheme HostingApp, configuration Release, destination generic/platform=iOS, one job per CPU, and CODE_SIGN_IDENTITY/DEVELOPMENT_TEAM overrides; its stdout is piped into xcbeautify. Then xcodebuild -exportArchive into <out>/ipa with repo/opts.plist. pod, xcbeautify and the export write to kbdgen’s stderr, so its stdout holds only results.

fastlane_env passes the target’s credentials to every fastlane run as MATCH_GIT_URL, MATCH_PASSWORD, FASTLANE_USER, PRODUCE_USERNAME, FASTLANE_PASSWORD and APP_STORE_KEY_JSON, on top of kbdgen’s own environment. The environment overrides of the target fields themselves (TEAM_ID, CODE_SIGN_ID, …) are applied when the bundle is loaded (bundle.structure.targets.env).

init (ios.build-chain.init) runs fastlane produce for the app and the app group, then one task per id that creates the App ID (except the base id), enables app groups and associates the group.

Toolchain

Each external tool is started with std::process::Command and its output captured; a non-zero exit becomes an error carrying the command’s stderr.

  1. git - the clone, above.

  2. In a run on 2026-11-17 they matched libdivvunspell-android-jniLibs-v1.0.0-beta.6.tgz and libpahkat-android-v2.3.1.tgz.

  3. tar - tar -xzf <download> -C app/src/main.

GenerateAndroid

GenerateAndroid::build does this, in order:

  1. Warns if no layout has an android section, then carries on.

  2. Creates assets/layouts, res/xml and res/xml-sw600dp, and lists the app’s res/values-* directories, which decide the languages it writes names for.

  3. Reads res/xml/method.xml and res/xml/spellchecker.xml and strips each back to the template’s subtypes (strip_subtypes). A subtype is kbdgen’s when its attributes are exactly what method_subtype or spellchecker_subtype writes for the tag (and keyboard name) it carries (generated_method_subtype, generated_spellchecker_subtype); all of those go, and their tags and keyboard names are what the last run generated. Only if there were none, and some layout has an android section, is the template’s first <subtype>, its placeholder, removed.

  4. For each layout, in bundle layout order:

    1. Flattens its transforms (flatten_transforms) into {dead key: {next: output}}. This runs before the android check, so it runs for every layout.

    2. Skips the layout if it has no android section.

    3. Derives the keyboard name from displayNames.en (keyboard_name): lowercase, ( and ) dropped, anything outside [a-z0-9] becomes x.

    4. Writes assets/layouts/{tag}.json (assets_layout): the transforms and the speller with android.config, else {"transforms": {}, "speller": null}.

    5. Writes the rows and row keys of primary to res/xml and of tablet-600 to res/xml-sw600dp (create_and_write_rows_keys_for_layer), deleting row key files numbered past the last row, then res/xml/kbd_{name}.xml and res/xml/keyboard_layout_set_{name}.xml.

    6. Sets english_ime_name in res/values/strings-appname.xml (set_ime_name), and collects the subtype_{sub} strings it wants in res/values/strings.xml and, where res/values-{lang} exists, in res/values-{lang}/strings.xml; {sub} is the tag lowercased with - as _ (subtype_name).

    7. Appends its <subtype> to method.xml and to spellchecker.xml.

  5. Deletes assets/layouts/{tag}.json for each tag the last run generated and this one did not, and the layout XML of each keyboard name likewise (remove_keyboard_files).

  6. Writes the subtype_{sub} strings (write_subtype_strings). The subtype_{sub} names of this run’s and the last run’s tags are kbdgen’s: values/strings.xml and every values-*/strings.xml end up with exactly the kbdgen strings this run wants in them. Paths are keyed by the file they resolve to, because values-en/strings.xml is a symlink to values/strings.xml. A file with nothing to set or remove is not read as XML or written.

  7. Sets english_ime_name from each project.yaml locale in res/values-{locale}/strings-appname.xml, where res/values-{locale} exists.

  8. Writes method.xml and spellchecker.xml.

  9. Generates the launcher icons (generate_icons).

  10. Writes app/local.gradle (generate_gradle_local) and runs Gradle (run_gradle), or warns that targets/android.yaml is missing.

Every string is set with set_string, which replaces the text of an existing <string> of that name and removes its duplicates rather than appending another. Together with the subtype stripping, that makes generation idempotent: android build reuses an existing {out}/repo, and giellakbd-android’s README tells developers to re-run android generate, so running it N times with one bundle must leave the files one run leaves. A checkout that older kbdgen versions appended to several times is repaired the same way.

XML is read, queried and written with xmlem. Every file kbdgen touches is written back pretty-printed, so git diff in the checkout shows whole files reformatted, and text such as a <string> value gains surrounding whitespace, which the Android resource compiler trims. Reading xmlem’s output and printing it again gives the same bytes (it trims text before indenting it), which idempotence relies on.

Known gaps

The engine module

crates/kbd-wasm is a cdylib over kbd-engine and kbd-model. It builds for wasm32-unknown-unknown with no imports, and exports memory and a C ABI of integers; there is no wasm-bindgen and no generated JavaScript, so a host needs only WebAssembly.instantiate(bytes, {}).

Text crosses the boundary as UTF-8 in two buffers the module owns. The host calls kbd_input(len), writes len bytes at the address it returns, then makes the call that reads them. Results are read from the output buffer before the next call. Any call may grow the memory, so the host takes a fresh view of memory.buffer after each one.

A loaded model is a session: the model and its engine State, named by a handle of at least 1. kbd_key runs Model::key with the session’s state and keeps the next state, so the host never holds engine state; it only resets it.

Export Meaning

kbd_input(len) -> addr

Sizes the input buffer to len zero bytes and gives its address.

kbd_load(len) -> handle

Loads the DVKB model in the first len input bytes into a new session. 0 on failure, with the error message as output.

kbd_unload(handle)

Drops the session; its handle is reused.

kbd_key(handle, key, modifiers, context_len, flags) -> i32

Sends a key, with the UTF-8 context before the caret in the first context_len input bytes. Returns 0 pass, 1 edit, -1 no such session, -2 unknown key or modifier bit, -3 context not UTF-8, -4 the instance is busy.

kbd_output() -> addr, kbd_output_len() -> len

The output buffer: after an edit, the inserted text then the preedit.

kbd_insert_len() -> len

How many bytes of the output are the inserted text.

kbd_delete() -> n

How many scalar values the edit deletes before the caret.

kbd_reset(handle)

Resets the session’s state.

kbd_pending(handle) -> n

How many markers are pending (Model::pending_markers): whether a Commit would type anything.

kbd_context_len(handle) -> n

Model::context_len.

kbd_extra_modifiers(handle) -> bits

The keys bound as extra modifiers, two bits per slot from extra1: 1 Right Ctrl, 2 Caps Lock, 3 B00.

kbd_shift_lock(handle) -> 0 or 1

Whether Caps Lock works as Shift Lock on this keyboard.

key is a scan code below 0x100, or 0x100 Decimal, 0x101 Backspace, 0x102 Commit. modifiers has one bit per ModifierState field: bit 0 shift_l, 1 shift_r, 2 caps, 3 ctrl_l, 4 ctrl_r, 5 alt_l, 6 alt_r, 7 altgr, 8 cmd, 9 to 11 extra1 to extra3. flags bit 0 is at_start and bit 1 authoritative. Every session runs with OutputForm::Nfc, BackspacePolicy::CancelOrPass and host chromeOS.

No export may panic. The crate denies panic, unwrap, expect, indexing and unreachable!; every failure is a return code. All state is one thread-local Instance, which with_instance borrows, giving a fallback value instead of panicking if it cannot. The only unsafe construct is no_mangle on the exports, all prefixed kbd_, and no export dereferences a raw pointer: the host reads and writes the module’s own Vec buffers through memory.

background.js repeats the key codes, modifier bits, flags and results as constants. Change the ABI in both; the typing test fails if they disagree.

How kbdgen embeds the module

build.rs runs a nested cargo:

cargo build --package kbd-wasm --release --locked \
  --target wasm32-unknown-unknown \
  --manifest-path <workspace>/Cargo.toml \
  --target-dir $OUT_DIR/kbd-wasm \
  --config 'profile.release.opt-level="s"' --config profile.release.lto=true \
  --config profile.release.codegen-units=1 --config 'profile.release.panic="abort"' \
  --config profile.release.strip=true

and copies wasm32-unknown-unknown/release/kbd_wasm.wasm to $OUT_DIR/kbd_wasm.wasm, which generate_chromeos.rs includes.

  • The nested build has its own target directory, because the outer build holds the lock on its own and the nested one would wait forever.

  • The size settings are passed with --config, so they apply to the nested build only.

  • It removes CARGO_ENCODED_RUSTFLAGS, RUSTFLAGS, CARGO_BUILD_RUSTFLAGS, RUSTC_WORKSPACE_WRAPPER, CARGO_TARGET_DIR and CARGO_BUILD_TARGET from its environment: they belong to the host build, or to clippy when this runs under cargo clippy.

  • It reruns only when crates/kbd-wasm, crates/kbd-engine/src, crates/kbd-engine/Cargo.toml, crates/kbd-model/src, crates/kbd-model/Cargo.toml or Cargo.lock change.

Building from the same workspace keeps the engine in every extension in step with the model encoding that kbdgen writes, and lets a released binary generate an extension without a Rust toolchain. No built module is checked in. Without the target installed, the build script panics with:

kbdgen: building kbd-wasm for wasm32-unknown-unknown failed with <status>. The ChromeOS target embeds kbd-engine compiled to WebAssembly; if the target is missing, install it with `rustup target add wasm32-unknown-unknown`

The module is about 230 KB.

The service worker

background.js registers every listener synchronously on its first evaluation, as a Manifest V3 service worker must. It never logs typed text or keys.

Loading

loadEngine fetches engine.wasm once and instantiates it; loadSession fetches models/<engine id>.dvkb, loads it and reads the extra-modifier keys and Shift Lock from it. onActivate starts loading the activated input method. A key that arrives before its session has loaded, or while earlier keys still wait, is queued on one promise chain: the listener returns undefined, and the key is answered later with keyEventHandled(requestId, handled), so keys apply in arrival order.

Keys

A key down is classified by KeyboardEvent.code, never by key (ldml.chromeos.keys):

  • Shift, Ctrl, Alt, Meta/OS (the Search key) and Caps Lock are modifiers: they pass and reset nothing.

  • Backspace is Backspace. NumpadDecimal is Decimal, unless its key is Delete (Num Lock off).

  • A code in SCAN_CODES, the PC/AT set 1 scan codes without E0, is sent as that scan code.

  • Any other code, such as the arrows, Delete or NumpadEnter, is a frame key: it passes and resets the state.

Key ups pass. Every key down and up updates the set of keys seen held, which gives modifiers their side, and the Shift Lock state (Caps Lock sets it, Shift clears it). modifierBits turns a captured event into kbd_key bits: Right Alt is alt_r and altgr whether the XKB layout beneath reports it as AltGr or as Alt, Left Alt is alt_l (which the engine passes on ChromeOS), Search held is cmd, Caps Lock is caps or, on a Shift Lock keyboard, the Shift Lock state, and a held Caps Lock or IntlBackslash bound as an extra modifier sets its extra bit (ldml.chromeos.modifiers).

Edits

handle sends an engine key with the context and applies the result (ldml.chromeos.semantics):

  • No focused field, or a modifier: the key passes.

  • A frame key, or an engine key the engine passes: pass sends Commit first if a composition is shown or kbd_pending is non-zero, applies its edit, then resets. The listener returns false.

  • An edit: apply calls, as needed and in this order, clearComposition (when text changes under a shown composition, or the preedit empties), deleteSurroundingText with offset −u and length u, commitText of the inserted text, and setComposition of the preedit with the cursor at its end. u is the UTF-16 length of the last delete scalar values of the context, since ChromeOS counts UTF-16 units. The listener returns true.

A password field gets an empty context and no flags, and shows no preedit. An exception, or a rejected IME call, resets the session and forgets the context.

Context

ChromeOS reports the text around the caret only afterwards, through onSurroundingTextChanged, at most 100 characters each way, and does not say whether that text includes the composition (ldml.chromeos.context). So field keeps its own view:

  • text, the committed text before the caret, at most 128 scalar values (MAX_CONTEXT; a model’s context_len is at most 64). Each edit updates it; a passing key keeps it, since a change brings a notification.

  • snapshots, the states the glue’s own IME calls lead to, oldest first, at most 64.

reconcile matches each reading, the text before the focus, against the snapshots from newest to oldest, with the composition stripped and not; two texts agree when one ends with the other. A reading of the newest snapshot completes the context and makes it authoritative; a reading of an older one lags and is dropped; any other reading replaces the context, keeping the engine state. A reading with a selection makes the next key reset and start from an empty context. at_start is set when the reading’s offset is 0.

onFocus, onBlur, onActivate and onDeactivated forget the held keys, reset every session and forget the context. onReset, which ChromeOS sends when it ends the input session, resets the sessions and forgets the context. All of this lives in the service worker’s globals, so when Chrome stops an idle worker a pending dead key goes with it.

The XKB tier

xkb::adapt turns one layout’s keyboard into its symbols file, its registry entry and its report:

  1. Keys (ldml.linux.keycodes). The written keys are those of the layout’s form among the 49 ISO positions, the JIS yen key and the space bar, by xkeyboard-config’s keycodes/evdev names, and <KPDL> for the decimal. A scan code’s evdev key code is kbd_model::evdev_code, which the IBus engine reads keys by too.

  2. Levels (ldml.linux.levels). Each key has eight states, the combinations of Shift, Lock and Level3, and each state takes the layer the engine selects for shift_l, caps and AltGr. When a Level3 state has a layer, the model uses Level3 and the file includes level3(ralt_switch); otherwise Right Alt stays Alt. Native-only layers and layers that only Left Alt, Left Ctrl or an extra modifier selects are not written.

  3. Values (ldml.linux.values). A state’s keysym is that of its output as the engine commits it, in NFC: for one scalar value, the keysym xkb_utf32_to_keysym gives, looked up in data/keysyms.tsv, a table read from libxkbcommon 1.13.1 itself; for a dead key, its dead keysym; for anything longer, VoidSymbol.

  4. Types (ldml.linux.types). types::choose takes the first of xkeyboard-config’s types that gives all of a key’s values under libxkbcommon’s semantics, Lock’s uppercasing included (ldml.linux.semantics). A key no type serves takes the one that gives the most states, and the states it gets wrong are reported.

  5. Dead keys (ldml.linux.dead-keys). Each dead key gets the first dead keysym, in the order of IBus’s table, whose character is its standalone or its display. dead_keys.rs then runs the engine from each pending marker, through chains of up to three keys, and compares it with compose.rs, which composes as IBus’s simple engine does on the reference Compose table: the <dead_…> sequences of libX11’s en_US.UTF-8/Compose.pre, vendored as data/Compose with their notices (ldml.linux.compose). Results that differ are reported. No Compose file is written.

classify.rs reports what the layout loses (ldml.linux.classify), as information that the IBus engine types it, except layers only Left Alt or Left Ctrl selects, which are warnings. registry.rs writes each <configItem> and the bundle’s rules/evdev.xml.

The D-Bus surface

ibus-daemon reads the component file, runs its engines command (--xml), and runs it again when an observed data directory changes. To use an engine it starts --ibus, which connects to ibus-daemon’s own bus, exports org.freedesktop.IBus.Factory at /org/freedesktop/IBus/Factory and owns org.freedesktop.IBus.Divvun. zbus spawns no task per call, so one thread handles every call in the order it arrives.

  • CreateEngine(name) loads the keyboard’s model and exports an engine at /org/freedesktop/IBus/Engine/<n>. A name it cannot serve fails with org.freedesktop.DBus.Error.Failed and the reason: no-description, model-unreadable, model-version, model-malformed or model-invalid (linux.ibus.inert).

  • An engine object implements org.freedesktop.IBus.Engine: ProcessKeyEvent, FocusIn, FocusOut, FocusInId, FocusOutId, Reset, Enable, Disable, SetCapabilities, SetSurroundingText and SetCursorLocation act, and the other methods succeed and do nothing. It emits CommitText, UpdatePreeditText, DeleteSurroundingText and RequireSurroundingText, the last two of which libibus’s introspection data lacks. Its properties are ContentType, FocusId (false) and ActiveSurroundingText (true), the last two a plain b, which is what ibus-daemon reads. org.freedesktop.IBus.Service.Destroy unexports it.

  • A call’s signals go out before its reply, in order, so ibus-daemon handles them first. The program exits when its connection closes.

The planner

A Session is one engine object’s state. process_key_event(keyval, keycode, state) returns a Reply: whether the key was handled, and the signals to emit before replying. focus_in, focus_out, reset, enable and disable return signals too, and set_capabilities, set_content_type and set_surrounding_text record what the client says. Every session runs the engine with OutputForm::Nfc, BackspacePolicy::CancelOrPass and host linux.

  • keys::classify identifies a press by its evdev key code, never by its keyval, which comes from whatever keymap is active (linux.ibus.keys). Keys tracks which modifier keys are held, for their sides, and turns IBus’s state bits into the engine’s modifiers (linux.ibus.modifiers). A press with key code 0 is a key of GNOME Shell’s on-screen keyboard: its keyval’s character is sent as Emit (linux.ibus.virtual-keys).

  • Where the context comes from depends on the field (Mode). A client with IBUS_CAP_SURROUNDING_TEXT reports its text, and context::Surrounding reconciles each reading with the engine’s own edits (linux.ibus.context). Without it, the context is the engine’s own edits, and for a model that rewrites committed text (ldml.linux.rewrites) the last context_len scalar values are held back as preedit, since such a client cannot be relied on to delete (linux.ibus.context.fallback). A password or PIN field gets no preedit and no context (linux.ibus.security).

  • An engine edit becomes, in order, a preedit clear, a DeleteSurroundingText, a CommitText and a preedit update (linux.ibus.edit). When markers are pending and nothing else would be shown, as after a dead key with standalone: '', the trailing marker’s display is shown with IBUS_ENGINE_PREEDIT_CLEAR, so that a reset drops it and GNOME Shell’s on-screen Backspace, which deletes past the engine unless a preedit is shown, reaches the engine (linux.ibus.osk-backspace).

Panics and logging

One process serves every input context, so a panic that unwound out of a call would end them all (linux.ibus.panic). The crate must build with panic = "unwind", the default, and guard.rs fails to compile otherwise. Every method call and property access runs its body in Process::contain, which catches a panic, logs its location, and gives the entry point’s fallback reply: false to ProcessKeyEvent, org.freedesktop.DBus.Error.Failed poisoned to CreateEngine, success to the rest. The process is then poisoned: it passes every key, emits nothing, creates no engine, and exits once ibus-daemon has destroyed its last engine object, so the next activation starts a fresh one. Meanwhile the XKB layout types. guard::faults::arm makes the next call of an entry point panic, for the tests.

The engine records no typed text, surrounding text, preedit, keyvals, key codes or engine states (linux.ibus.logging). diag::record writes one line to standard error, ibus-engine-divvun: <event>, and an Event can hold only a message compiled into the program, an inert reason with a file name, or a panic’s file, line and column, never its message. ibus-daemon passes the line on to its own standard error only when it runs with --verbose. tests/self_contained.rs checks that nothing else in the program prints, writes files, starts processes or opens network connections.

The on-screen keyboards

osk::present builds one presented set from the keyboard’s hardware layers (ldml.linux.touch): a default level from the layer for no modifier, a shift level from the Shift layer when there is one, and two symbol levels that are the same for every layout, with backspace and shift or symbol-switch keys added. Each on-screen keyboard’s writer maps it to its own format:

  • gnome.rs writes GNOME Shell’s JSON (ldml.linux.touch.gnome). A dead key whose dead keysym the XKB layout has at Level1, 2 or 3 is written as that keyval, so GNOME Shell presses it on its virtual keyboard and it reaches the IBus engine as a hardware key. The layouts go into osk-layouts.gresource, which kbdgen writes itself in GVDB format with the gvdb crate, so no glib-compile-resources is needed. extension.js is osk/gnome/extension.js, included unchanged.

  • plasma.rs writes each layout’s KPackage: metadata.json and contents/layouts/desktop.qml (ldml.linux.touch.plasma).

  • stevia.rs writes Stevia’s JSON (ldml.linux.touch.stevia).

osk/classify.rs reports, for each on-screen keyboard, what it does not show or type (ldml.linux.classify.touch).

Tests that need Linux tools

fixtures_compile_list_and_type_in_libxkbcommon compiles each fixture’s keymap with the output’s xkb/ ahead of the default include paths, requires no warning beyond those compiling us gives, finds the layout in libxkbregistry, and types every key in all eight states through xkb_state_key_get_one_sym and xkb_state_key_get_utf8. It uses the xkbcommon crate, a dev-dependency on Linux only, and links libxkbcommon only when build.rs has set kbdgen_xkbcommon, which it does for a Linux target when pkg-config --exists xkbcommon xkbregistry succeeds. Otherwise it prints

linux.test.xkbcommon skipped: pkg-config found no xkbcommon and xkbregistry for this target

and passes.

crates/kbd-ibus/tests/ibus.rs runs the built ibus-engine-divvun under a private ibus-daemon: its own address, HOME and XDG_* directories in a temporary directory, and IBUS_COMPONENT_PATH naming a directory with only the engine’s component. Acting as the client over D-Bus, it creates an input context, types the planner’s cases and applies the signals to a fake field, and it checks the engine list against --xml and CreateEngine of a corrupt model. It runs the ibus-daemon that IBUS_DAEMON names, else the one on PATH, and needs a session bus, so run it under dbus-run-session. Without ibus-daemon, each of its tests prints

engine_registers: ibus-daemon is not installed; skipping (linux.test.ibus)

and passes. fixtures_type_through_the_daemon takes a few minutes.

With KBDGEN_REQUIRE_LINUX_TESTS set, both fail instead of skipping (linux.test.ci). A Linux CI job that runs the tests must install libxkbcommon’s development files, ibus and a D-Bus daemon, and set it, so that a job missing them fails rather than passing untested; CI on other hosts leaves it unset.

On macOS, run both in Docker, in a fedora:44 container, from the repository root:

docker run --rm -v "$PWD":/src:ro -v kbdgen-f44-target:/target fedora:44 sh -c 'dnf -y install ibus dbus-daemon dbus-tools gcc pkgconf-pkg-config libxkbcommon-devel; curl -sSf https://sh.rustup.rs | sh -s -- -y --profile minimal; . ~/.cargo/env; rustup target add wasm32-unknown-unknown; cd /src; KBDGEN_REQUIRE_LINUX_TESTS=1 CARGO_TARGET_DIR=/target dbus-run-session -- cargo test -p kbd-ibus --test ibus'

The named volume keeps the build between runs. To run the libxkbcommon test too, end the sh -c script with ; KBDGEN_REQUIRE_LINUX_TESTS=1 CARGO_TARGET_DIR=/target cargo test -p kbdgen --lib fixtures_compile_list_and_type_in_libxkbcommon -- --nocapture; it prints 0 problem(s) for each fixture.

No automated test runs GNOME Shell, KWin, plasma-keyboard, Phosh or a Wayland client. The scripts in tests/linux-vm/ do, by hand; each directory’s README.md says how to run it:

gnome-spike/

The experiment behind "GNOME spike results" in docs/spec/linux.md: a headless GNOME Shell 50 or 51 in a Lima VM, a logging IBus engine and a GTK 4 field, checking that an extension can add on-screen layouts through a GResource bundle and how on-screen keys reach an engine.
