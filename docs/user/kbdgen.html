kbdgen builds keyboard layouts for Windows, macOS, ChromeOS, iOS and Android from one source: a .kbdgen bundle, which is a directory of YAML files describing the layouts, plus per-target metadata and resources such as icons. It also converts layouts to and from CLDR LDML Keyboard 3.0 XML, and runs typing tests against kbdgen’s keyboard engine.

This guide covers the command line, the bundle, the two layout formats, layout tests, and what each target produces. Contributors will find the internals in the developer guide, and the normative specification in docs/spec/ in the repository.

kbdgen is built from source. With Rust installed through rustup:

rustup target add wasm32-unknown-unknown
git clone https://github.com/divvun/kbdgen.git
cd kbdgen
cargo install --path .

The WebAssembly target is needed because kbdgen’s build compiles its keyboard engine to WebAssembly for the ChromeOS target. Some targets need more tools, such as the Windows Rust targets or Xcode; each target’s chapter lists them.

Command line

kbdgen is one binary with four commands:

Command What it does

kbdgen target

Builds a bundle’s keyboards for one platform: Windows, macOS, ChromeOS, iOS or Android.

kbdgen ldml

Works on a bundle’s layouts: exports them to CLDR LDML Keyboard 3.0 XML, imports XML, migrates format 3 layouts to format 4, compiles engine models, and runs layout tests.

kbdgen fetch

Downloads layouts that the bundle takes from other keyboard repositories.

kbdgen tsf

Builds the Windows text service for release. This is release engineering for the text service itself, not part of building a keyboard.

Every command and subcommand prints its usage with --help, and kbdgen --version prints the version.

Output, logging and exit status

kbdgen writes its log to stderr. Each line has a timestamp, a level and the module that wrote it:

2026-11-17T22:47:55.734906Z  INFO kbdgen::build::windows::kbdl::build: Building kbdtsfa for x64

The default level is info: one line per milestone, plus every warning. The RUST_LOG environment variable changes it:

RUST_LOG=warn kbdgen target -b sme.kbdgen -o out/windows windows    # warnings only
RUST_LOG=debug kbdgen target -b sme.kbdgen -o out/windows windows   # each file written, each tool run
RUST_LOG=info,kbdgen::build::windows=trace kbdgen target -b sme.kbdgen -o out/windows windows

The last form raises one module to trace, which includes the full output of the tools kbdgen runs (cargo, for Windows). Start such a list with a default level such as info: a RUST_LOG that names only a module silences everything else.

Stdout carries only a command’s results, so it can be piped or captured:

  • the files that ldml export, ldml compile, ldml import and tsf wrote, one path per line (ldml import prints its notes and warnings before them)

  • the identifiers from target … ios print-pkg-ids

  • the report of ldml migrate and the results of ldml test

The one exception is target … ios build: pod install and xcodebuild print their own progress to stdout while they run.

kbdgen exits with status 0 on success. On failure it prints Error: and the reason to stderr, followed by Caused by: lines when there is more detail, and exits with status 1. A command line that does not parse exits with status 2 and prints the usage.

kbdgen target

kbdgen target -b <BUNDLE> -o <OUT> <PLATFORM> [<STEP>] [OPTIONS]
-b, --bundle-path

The .kbdgen bundle directory (Bundles).

-o, --output-path

The output directory. kbdgen creates it, with its parents, when it does not exist.

Both options are required and come before the platform: kbdgen target windows -b … is a usage error.

kbdgen first loads the whole bundle: project.yaml, every layout, the target files and the resources. When anything fails to load, it stops before creating the output directory. iOS and Android then refuse a bundle that has any format 4 layout:

Error: layout vro is a v4 layout (`format: 4`); the ios target cannot build v4 layouts yet

Windows, macOS and ChromeOS build format 3 and format 4 layouts side by side.

Platform and step What it does

windows

Generates a Rust crate per layout in OUT/build/, then builds each into layout DLLs in OUT/x86/, OUT/x64/, OUT/arm64/ and OUT/wow64/.

chromeos

Writes an input method extension into OUT: manifest.json, background.js, engine.wasm, one model per layout in models/, and _locales/.

macos build

Runs generate, then installer. --no-installer skips the installer. A kbdgen built for another operating system than macOS skips the installer with a warning.

macos generate

Writes the keyboard layout bundle OUT/<packageId>.keyboardlayout.<bundle>.bundle, with one .keylayout file per layout.

macos installer

Packages that bundle as OUT/<packageId>.keyboardlayout.<bundle>.pkg, with pkgbuild and productbuild. Run generate first.

ios build

Clones giellakbd-ios into OUT/repo, generates the keyboards and the Xcode project, downloads signing certificates and provisioning profiles with fastlane, runs pod install, then archives and exports the app to OUT/<packageId>.xcarchive and OUT/ipa/.

ios print-pkg-ids

Prints the app’s bundle identifier and each keyboard’s, one per line, sorted. Runs no build step.

ios init

Registers the app and keyboard identifiers, and their app group, with App Store Connect through fastlane.

android build

Runs clone, downloads the divvunspell and pahkat libraries from their GitHub releases into the app, then runs generate.

android clone

Clones giellakbd-android into OUT/repo. An existing OUT/repo is reused.

android generate

Writes the layouts, names, icons and spell checker configuration into OUT/repo. When the bundle has targets/android.yaml, it also writes app/local.gradle and runs gradlew assembleRelease.

Each step either completes or stops the build with an error; a full build runs its steps in order and stops at the first failure. The target chapters describe each platform’s configuration and output in detail.

Build the Windows layout DLLs:

kbdgen target -b sme.kbdgen -o out/windows windows

Build the macOS bundle and its installer:

kbdgen target -b sme.kbdgen -o out/macos macos build

Build the ChromeOS extension:

kbdgen target -b sme.kbdgen -o out/chromeos chromeos

List the iOS bundle identifiers, for example to set up signing:

kbdgen target -b sme.kbdgen -o out/ios ios print-pkg-ids

kbdgen ldml

The ldml commands work on the layouts in the bundle’s layouts/ directory; ldml test also reads tests/. They do not read project.yaml, the target files or the resources. Here -b and -o come after the subcommand.

export and compile work on format 4 layouts only, and fail on a format 3 layout with a hint to migrate it. Both take two filters, each repeatable:

--layout <TAG>

Only this layout. A tag that names no layout is an error. Use it to pick format 4 layouts out of a bundle that still has format 3 ones.

--host <HOST>

Only this host: windows, macOS, chromeOS, linux, iOS, android or web. The names are case-sensitive.

Without filters they cover every layout and every host. A layout has a keyboard for some hosts only; the others are skipped. export, compile and import check everything before they write the first file, so a failure leaves nothing behind.

The examples below start from the format 3 bundle sme.kbdgen, and migrate it first.

ldml migrate

kbdgen ldml migrate -b <BUNDLE> [--dry-run] [--report <FILE>]

Converts the bundle’s format 3 layouts to format 4, in place. For each layout it lists the defects it found: what the conversion changed, what it dropped, and what to review, each with a code such as M09 and the action taken. A layout with a blocking defect is not written, and the command then exits with status 1; the other layouts are still written. Moving to format 4 lists the defects and how to resolve the blocking ones.

--dry-run

Report only; write no layout.

--report <FILE>

Write the report to FILE as YAML (the defects, then a summary with each layout’s outcome), and print only the summary.

Preview, then convert and keep the report:

kbdgen ldml migrate -b sme.kbdgen --dry-run
kbdgen ldml migrate -b sme.kbdgen --report migration.yaml

The report ends with a summary and the state of each layout:

summary: 4 layout(s), 29 defect(s): M06 1, M09 6, M13 3, M14 14, M16 5
sme.kbdgen/layouts/se.yaml: written
sme.kbdgen/layouts/se-FI.yaml: written

ldml compile

kbdgen ldml compile -b <BUNDLE> -o <OUT> [--layout <TAG>]… [--host <HOST>]…

Writes OUT/<tag>.<host>.dvkb, the binary engine model of each layout for each host. These are the models that the Windows DLLs and the ChromeOS extension embed; compiling them on their own is the quick way to check a layout while writing it (Checking a layout).

kbdgen ldml compile -b sme.kbdgen -o out/models --host windows

ldml export

kbdgen ldml export -b <BUNDLE> -o <OUT> [--layout <TAG>]… [--host <HOST>]…

Writes OUT/<tag>.<host>.xml, an LDML Keyboard 3.0 document per layout and host. What LDML cannot express goes into elements in kbdgen’s own namespace, which other LDML tools ignore. LDML Keyboard 3.0 shows how a layout maps to LDML.

kbdgen ldml export -b sme.kbdgen -o out/xml --layout se-NO

ldml import

kbdgen ldml import -b <BUNDLE> [--force] <XML>…

Reads LDML Keyboard 3.0 files and writes each layout as layouts/<tag>.yaml in format 4. Files for the same layout, one per host, are merged into one layout. The tag comes from kbdgen’s own attribute when a file has it (files kbdgen exported do), otherwise from the keyboard’s locale. An existing layout file is an error unless --force is given.

The command prints how many XML comments each file lost, any warnings, and the files it wrote:

kbdgen ldml import -b my.kbdgen --force out/xml/*.xml

ldml test

kbdgen ldml test -b <BUNDLE> [--cldr]

Runs every tests/*.yaml file of the bundle through the engine and prints each failing step with the expected and actual result, then a summary. It exits with status 1 when a step fails. --cldr also runs the CLDR test vectors that kbdgen carries. Testing layouts describes the test file format.

$ kbdgen ldml test -b my.kbdgen
FAIL tests/dead-keys.yaml: deliberately wrong: step 2: expect
  expected text     "b"
  actual   text     "a"
  actual   preedit  ""
  actual   layer    none
  actual   action   edit: delete 0, insert "a", preedit "", layer none
files: 1, tests: 2, checks: 3, failing steps: 1
Error: 1 conformance steps failed

kbdgen fetch

kbdgen fetch -b <BUNDLE>

Copies the layouts listed under dependencies in project.yaml from other bundles on GitHub into this one, replacing files already there (Dependencies and kbdgen fetch). With this in my.kbdgen/project.yaml:

dependencies:
  sme:
    url: giellalt/keyboard-sme
    layouts: [se]
kbdgen fetch -b my.kbdgen

writes my.kbdgen/layouts/se.yaml and my.kbdgen/projects/se.yaml.

kbdgen tsf

kbdgen tsf -w <WORKSPACE> -o <OUT>

Builds the Windows text service, which every Divvun keyboard on Windows shares and which is released separately from keyboards.

-w, --workspace

A kbdgen checkout, which holds crates/kbd-tsf.

-o, --output-path

Where to write the release files.

It builds divvun_tip_x86.dll, divvun_tip_x64.dll and divvun_tip_arm64.dll, checks each, links the Arm64X forwarder divvun_tip.dll, and prints the four files' absolute paths on stdout: the list of files to sign. The DLLs link the Rust standard library against the MSVC and Windows SDK libraries, so this runs on Windows, with the MSVC build tools, the Windows SDK and the three Windows Rust targets installed.

kbdgen tsf -w . -o release

Bundles

A bundle is a directory, by convention named <name>.kbdgen, that holds everything kbdgen needs to build the keyboards of one project: the layouts, the settings of each target platform, and resources such as icons. Every command that works on a bundle takes its path with -b (--bundle-path).

The keyboard-* repositories of the GiellaLT project are complete, real bundles; keyboard-sme holds sme.kbdgen, for Northern Sami.

What a bundle contains

sme.kbdgen/
├── project.yaml        names, author, copyright; dependencies for kbdgen fetch
├── layouts/            one file per keyboard layout, named by language tag
│   ├── se.yaml
│   ├── se-FI.yaml
│   └── se-NO.yaml
├── targets/            one file per target platform
│   ├── windows.yaml
│   ├── macos.yaml
│   └── ios.yaml
├── resources/          icons and other files, one directory per target
│   ├── macos/
│   │   ├── icon.png
│   │   └── icon.se-NO.png
│   └── ios/
│       └── icon.png
├── projects/           optional: written by kbdgen fetch
└── tests/              optional: typing tests for kbdgen ldml test

project.yaml and the directories layouts/, targets/ and resources/ must all exist, even when a directory is empty. If one is missing or cannot be read, kbdgen target and kbdgen fetch stop with an error before doing anything else.

  • In layouts/ and targets/, kbdgen reads only files whose extension is exactly .yaml. It skips everything else without a word, including .yml files.

  • projects/ is where kbdgen fetch copies the project.yaml of each dependency (Dependencies and kbdgen fetch); the iOS target reads it.

  • tests/ holds the typing tests that kbdgen ldml test runs (Testing layouts).

The bundle’s name is its directory name without the extension: sme.kbdgen is the bundle sme. Some targets use it in identifiers, so pick it once and keep it.

project.yaml

project.yaml describes the project as a whole.

locales:
  en:
    name: Sami Keyboards
    description: Keyboards for the Sami languages.
  se:
    name: Sámi boallobeavddit
    description: Boallobeavddit sámegielaide.
author: Example Author
copyright: (c) 2026 Example Organisation
email: feedback@example.org
organisation: Example Organisation
dependencies:
  sme:
    url: giellalt/keyboard-sme
    layouts: [se, se-FI]
  smj:
    url: giellalt/keyboard-smj
    branch: main
    layouts: [smj-NO, smj-SE]
Field Required Meaning

locales

yes

The name and description of the keyboard package, in each language of the user interface, keyed by language code. Each entry needs both name and description. The iOS, Android and ChromeOS targets use these for the app or extension; ChromeOS needs an en entry.

author

yes

The author.

copyright

yes

The copyright line. Windows writes it into each layout’s version information.

email

yes

A contact address.

organisation

yes

The organisation. Windows writes it into each layout’s version information as the company.

dependencies

no

Other bundles to copy layouts from with kbdgen fetch (Dependencies and kbdgen fetch).

Any plain value is read as text, so copyright: 2026 is fine here. Fields kbdgen does not know are ignored.

Dependencies and kbdgen fetch

A bundle can collect layouts that live in other repositories. Each entry under dependencies names the source bundle and the layouts to copy:

  • the entry’s key is the name of the source bundle: sme for sme.kbdgen;

  • url is the GitHub repository, as owner/repository;

  • layouts lists the language tags of the layouts to copy;

  • branch is the branch to copy from; it defaults to main.

kbdgen fetch -b divvun.kbdgen

For each dependency, in order, kbdgen fetch downloads https://github.com/<url>/archive/<branch>.zip, finds <key>.kbdgen in it, and for each listed layout copies

  • its layouts/<tag>.yaml to layouts/<tag>.yaml of your bundle, and

  • its project.yaml to projects/<tag>.yaml of your bundle,

replacing files that are already there. It creates layouts/ and projects/ if needed. A url without a / or a failed download stops the command with an error naming the dependency, and a missing layout with one naming the file. Files copied before the error stay.

Target files

Each file in targets/ configures one target platform, and its name says which: windows.yaml, macos.yaml, ios.yaml, android.yaml and chromeos.yaml. kbdgen warns about any other name and ignores the file. That includes chrome.yaml, the name older bundles use: rename it to chromeos.yaml. Without its file a target is unconfigured; the chapter on each target says what it needs.

These are the fields. The target chapters explain what each one does.

Some rules hold for every target file:

  • Fields kbdgen does not know are ignored, so a misspelt optional field is silently missing. Check the spelling against the table.

  • windows.yaml, macos.yaml and chromeos.yaml read any plain value as text: version: 1.0 is the version 1.0.

  • ios.yaml and android.yaml are stricter. Their text fields must be YAML strings, so quote anything YAML would read as a number: version: '1.0'. version: 0.1.0 needs no quotes, as it is not a number. Unquoted, kbdgen stops with an error such as version: invalid type: floating point `1.0`, expected a string.

  • A windows.yaml with a top-level shiftLock, lrmRlm or keyNames is an error. These are options of each keyboard, so they belong in the layout file as targets.windows.shiftLock and so on (Platform settings of a layout).

Resources

resources/ has one directory per target: macos, ios, chromeos and android. kbdgen warns about any other directory and ignores it, and ignores plain files directly in resources/. A ChromeOS directory may also be called chrome, as older bundles name it, but a bundle may not have both chrome and chromeos.

The resources kbdgen reads are icons:

  • icon.<ext>, such as icon.png, is the target’s default icon;

  • icon.<tag>.<ext>, such as icon.se-NO.png, is the icon of the layout whose language tag is <tag>.

Which icons each target uses:

Directory Icons used

macos

Each layout gets icon.<tag>.<ext> for its own tag, else the default icon.<ext>. kbdgen converts them to .icns when it runs on a Mac.

ios

Only the default icon.<ext>: the app has one icon for all its keyboards.

chromeos (or chrome)

Only the default icon, which must be a .png: the extension has one icon.

android

Only icon.png.

In macos, ios and chromeos these are errors:

  • a <tag> that is not a language tag: icon.se_FI.png (write icon.se-FI.png);

  • two icons for one tag: icon.se-FI.png and icon.se-fi.icns;

  • two default icons: icon.png and icon.icns.

Layouts

Each file in layouts/ is one keyboard layout, and its name is the layout’s language tag (BCP 47): se.yaml, se-FI.yaml, smj-NO.yaml. kbdgen normalises the case, so se-fi.yaml is the layout se-FI. A name that is not a language tag, such as se_FI.yaml, stops loading with Failed to parse language tag.

A layout file comes in one of two formats:

  • Format 4, with format: 4 at the top: the current format, described in Writing layouts.

  • Format 3, with no format field: the format that the iOS and Android targets still need, described in Format 3 layouts. kbdgen ldml migrate converts it to format 4 (Moving to format 4).

One bundle may hold layouts in both formats. Any other value of format is an error.

Every layout must have its autonym: a displayNames entry, the layout’s name in its own language, keyed by the primary language subtag of its tag. For se-FI.yaml that key is se:

displayNames:
  se: Davvisámegiella (Suopma)
  en: Northern Sami (Finland)

An entry under the full tag se-FI alone does not count. Without the autonym, loading stops with Missing mandatory display name for language tag: `se-FI` for a format 3 layout, or displayNames has no autonym, a name for se for a format 4 one.

How kbdgen reads layouts/:

  • It reads the files in the order of their file names, compared byte by byte, and stops at the first one that is broken.

  • An empty file is an error: a layout must be a YAML mapping.

  • If two files name the same tag after normalisation (se-FI.yaml and se-fi.yaml), the later one replaces the earlier. Avoid this.

  • Everything kbdgen builds visits the layouts in the order of their tags, compared byte by byte: se, se-FI, sma, sme. That order is the same on every run.

  • Whenever kbdgen loads the bundle, it parses every layout file and checks format 3 layouts against their schema, so a broken file stops every command. It checks format 4 layouts in full only when something builds them; run kbdgen ldml compile to check them without building a target (Checking a layout).

Writing layouts

A layout file describes one keyboard for one language tag, on every platform at once. You write what each key types in each modifier state, as rows of characters, plus a table for each dead key. kbdgen generates the rest.

This chapter describes format 4, the format for new layouts. It is a guide, built around one example that grows section by section: Northern Sami as typed in Finland, layouts/se-FI.yaml. The complete file is at the end of the chapter (The complete layout). The exhaustive rules are in the specification, docs/spec/ldml/yaml.md.

Format 4 uses the vocabulary of the Unicode standard for keyboards, LDML Keyboard 3.0: its layer names, escapes and transform rules. Anything an LDML keyboard can say, a format 4 layout can say too, and kbdgen converts between the two (LDML Keyboard 3.0).

Checking a layout

While you write, compile the layout. This checks every format 4 layout of the bundle and builds it for every platform, without building a target:

kbdgen ldml compile -b sme.kbdgen -o /tmp/sme-models

In a bundle that also has format 3 layouts, name the format 4 ones, as in --layout se-FI; a format 3 layout here is an error that suggests migrating it. kbdgen checks everything before it writes the first file, so a mistake writes nothing. Format 4 is strict: an unknown field is an error, not something kbdgen quietly ignores. Every error names the file, the place in it, and for rows the row and token, counted from 1:

Error: ./layouts/se-FI.yaml: hardwar: unknown field hardwar
Error: ./layouts/se-FI.yaml: hardware.default.layers.none, row 2: layer none row 2 has 11 tokens; form iso row 2 has 12 scan codes
Error: ./layouts/se-FI.yaml: hardware.default.layers.none, row 1, token 13: no dead key has the identity "´"

To check what the layout types, write tests (Testing layouts).

A first layout

format: 4
displayNames:
  se: Davvisámegiella (Suopma)
  en: Northern Sami (Finland)
  fi: Pohjoissaame (Suomi)
hardware:
  default:
    layers:
      none: |
        § 1 2 3 4 5 6 7 8 9 0 + ´
        á š e r t y u i o p å ŋ
        a s d f g h j k l ö ä đ
        ž z č c v b n m , . -
      shift: |
        ½ ! " # ¤ % & / ( ) = ? `
        Á Š E R T Y U I O P Å Ŋ
        A S D F G H J K L Ö Ä Đ
        Ž Z Č C V B N M ; : _

This is already a working keyboard for Windows, macOS and ChromeOS.

  • format: 4 marks the file as format 4. Without it, kbdgen reads the file as format 3 (Format 3 layouts).

  • displayNames names the keyboard in several languages. The entry for the layout’s own language, here se, is required (Layouts).

  • hardware describes physical keyboards. default applies to every platform; Platforms and variants shows how one platform can differ.

  • layers maps each modifier state to what the keys type in it: none without modifiers, shift with Shift.

Rows and key positions

The | after a layer name starts a YAML block: the indented lines below it, taken as they are. Each line is one row of keys, and the keys of a row are separated by spaces. Extra spaces and blank lines do not matter, so you can line up the columns.

The four rows of the default form, iso, are the four rows of character keys on a European keyboard, with 13, 12, 12 and 11 keys. Each key has a name from the ISO keyboard standard, which tests and error messages use:

 E00 E01 E02 E03 E04 E05 E06 E07 E08 E09 E10 E11 E12   ← E00 left of 1, E12 left of Backspace
Tab  D01 D02 D03 D04 D05 D06 D07 D08 D09 D10 D11 D12   ← D01 right of Tab (Q)
Caps  C01 C02 C03 C04 C05 C06 C07 C08 C09 C10 C11 C12  ← C01 right of Caps Lock (A), C12 left of Enter
Shift B00 B01 B02 B03 B04 B05 B06 B07 B08 B09 B10      ← B00 right of Shift, left of Z

So in the first layout, § is E00, á is D01, đ is C12 and ž is B00. Other keyboard shapes have other row lengths; choose one with form:

You do not write the space bar: it types a space in every layer. To change that, see The space bar.

Writing characters

Each entry of a row, a token, is usually just the text the key types. It can be more than one character, such as a letter with a combining accent. Some tokens start with a backslash and mean something else:

Token Meaning

\u{A0}

The character U+00A0, by its hexadecimal code point (1 to 6 digits). Use it for anything you cannot see or type: spaces, no-break spaces, joiners, combining marks on their own (\u{301}).

\u{0}

No key: the key types nothing in this layer.

\d{´}

The dead key ´ (Dead keys).

\s{space}

A space bar key.

\s{gap}

An empty position.

\k{eng}

The key eng defined under keys (Explicit keys).

\s{shift}, \s{"@":0.75}, \l{accents}

Keys of touch layouts (Touch layouts).

A backslash that starts none of these is an ordinary backslash, so a key that types \ is written \. A \u that is not followed by { is an error: write \u{AD}, not \u00AD.

Tokens never contain spaces, because spaces separate them. A key that types a space is written \u{20}.

Quoting in YAML

Inside a | block nothing needs quoting. Elsewhere, YAML gives some characters a meaning of their own, so quote them with single quotes when they are the whole value or a key: '~' (unquoted it means "nothing"), '`', '#', '@', '%', '&', '*', '!', '|', '>', '?', '-', ':', ',', '[', '{', "'". Quote digits and numbers too, and the words YAML might read as true or false, such as 'y', 'n', 'no', 'on' and 'off'.

Format 4 never turns a number or a true/false into text behind your back: where it expects text and finds anything else, it stops and asks you to quote it:

Error: ./layouts/se-FI.yaml: decimal: expected a string, found 1; quote it

The same goes for { and } inside a value written in braces, such as keyNames: {space: gaska}: a value containing braces must be quoted there.

Caps Lock

The first layout has no caps layer, yet Caps Lock works as people expect: it types capitals, and leaves digits and punctuation alone. Caps Lock with Shift types capitals too. kbdgen derives these states from the layers you wrote:

  • For a layer such as none that has a shifted partner (shift), it creates the Caps Lock layer: each key types its shifted output when that is the capital of the unshifted one (á → Á), and its unshifted output otherwise (1, not !).

  • Caps Lock with Shift uses the shifted layer.

  • A layer with no shifted partner is used for Caps Lock as it is.

The same happens for alt and alt shift: Caps Lock with AltGr types Ǧ on C05. A layer you write yourself always wins, so write a caps layer when Caps Lock should do something else. To turn the derived layers off and get only the layers you wrote, put impliedLayers: none in the variant, next to layers.

One layer can serve several modifier sets, separated by commas. This layer is used both with Caps Lock and with Caps Lock and Shift, and its fifth row holds the space bar, here a no-break space:

      caps, caps shift: |
        § 1 2 3 4 5 6 7 8 9 0 + ´
        Á Š E R T Y U I O P Å Ŋ
        A S D F G H J K L Ö Ä Đ
        Ž Z Č C V B N M , . -
        \u{A0}

Two layers may not name the same modifier set.

The space bar

The space bar types a space unless you say otherwise, in one of two ways:

  • a fifth row with a single token, at the end of a layer, as in the caps, caps shift layer above;

  • a space entry in the variant, keyed by the layer’s name:

        space: {alt: '\u{A0}'}

Ctrl and Command layers

Layers whose modifiers include cmd, or ctrl without Alt, never type text: those key combinations are shortcuts, and kbdgen passes them to the application. Such a layer only tells the platform which character a shortcut key stands for. A cmd layer becomes the Command key map of the macOS .keylayout, and a ctrl layer the Ctrl column of the Windows layout DLL.

Extra modifier keys (Windows)

On Windows, up to three keys can act as extra modifiers, each selecting its own layers: the right Ctrl key (rightCtrl), Caps Lock (capsLock) and the ISO key left of Z (B00). extraModifiers binds them, in order, to extra1, extra2 and extra3. Here right Ctrl selects a Greek layer:

  windows:
    inherits: default
    extraModifiers: [rightCtrl]
    layers:
      extra1: |
        \u{0} \u{0} \u{0} \u{0} \u{0} \u{0} \u{0} \u{0} \u{0} \u{0} \u{0} \u{0} \u{0}
        ; ς ε ρ τ υ θ ι ο π \u{0} \u{0}
        α σ δ φ γ η ξ κ λ \u{0} \u{0} \u{0}
        \u{0} ζ χ ψ ω β ν μ \u{0} \u{0} \u{0}

Dead keys

A dead key types nothing at first; it changes the next key. The keyboard has six of them: acute ´ and grave ` on the key left of Backspace, and on D11 and D12 with AltGr the diaeresis ¨, tilde ~, circumflex ^ and caron ˇ. deadKeys gives each one a table, and \d{…} puts it on a key:

deadKeys:
  ´:
    compose:
      a: á
      A: Á
      e: é
      E: É
      ¨:
        compose: {u: ǘ, U: Ǘ}
  '`':
    compose: {a: à, A: À, e: è, E: È}
  ¨:
    compose: {a: ä, A: Ä, o: ö, O: Ö, u: ü, U: Ü}
  '~':
    compose: {a: ã, A: Ã, o: õ, O: Õ}
  ^:
    compose: {a: â, A: Â, e: ê, E: Ê}
  ˇ:
    compose: {c: č, C: Č, g: ǧ, G: Ǧ, s: š, S: Š, z: ž, Z: Ž}
hardware:
  default:
    layers:
      none: |
        § 1 2 3 4 5 6 7 8 9 0 + \d{´}
        á š e r t y u i o p å ŋ
        a s d f g h j k l ö ä đ
        ž z č c v b n m , . -
      shift: |
        ½ ! " # ¤ % & / ( ) = ? \d{`}
        Á Š E R T Y U I O P Å Ŋ
        A S D F G H J K L Ö Ä Đ
        Ž Z Č C V B N M ; : _

In the alt and alt shift layers, D11 and D12 become \d{¨} \d{~} and \d{^} \d{ˇ} (The complete layout).

The key of each deadKeys entry is the dead key’s identity: the character it stands for, which \d{…} names. compose maps what the next key types to the result. A dead key can appear on any number of keys and layers. One that no \d{…} uses has no effect: no platform gets it.

What the user gets

kbdgen’s keyboard engine, which ChromeOS and the Divvun text service on Windows run, gives dead keys the behaviour they have on macOS. The macOS .keylayout and the Windows layout DLL that kbdgen generates follow it as far as those formats allow. With ´ on the key left of Backspace:

  • ´ then a types á, and ´ then Shift+a types Á.

  • While a dead key waits, the text shows what it would type alone, here ´, marked as unfinished.

  • ´ then the space bar types ´ alone.

  • ´ then a key that is not in the table types the accent, then the key: ´ then f types ´f.

  • ´ then another dead key that is not in the table types ´, and the new dead key waits: ´ then ˇ then c types ´č.

  • Backspace while a dead key waits cancels the dead key and nothing else.

  • Committing the text while a dead key waits, for example by switching to another window, types the waiting accent.

Standalone output, chains and names

Each dead key can also have:

standalone

What the dead key types on its own: with the space bar or before a key it does not combine with. It is also what the text shows while the dead key waits. The default is the identity. Set it when the dead key’s character differs from what it should type alone, or to '' to make an unmatched dead key vanish:

deadKeys:
  ˜:
    standalone: '~'
    compose: {a: ã, o: õ}
  ¨:
    standalone: ''
    display: ◌̈
    compose: {a: ä, o: ö}

Here ˜ (the small tilde) types an ASCII ~ alone, and ¨ then f types just f. While ¨ waits, the text shows nothing, since its standalone output is empty.

display

The label of the dead key’s keycap on on-screen and touch keyboards. The default is the identity.

name

The dead key’s name in the Windows layout DLL’s table of dead-key names. Only top-level dead keys have one.

marker

The LDML marker id that kbdgen generates for the dead key, by default dk_ and the identity’s code points (dk_00B4). You rarely need it.

A compose value can itself be a dead key node, with its own compose, standalone and display. That chains dead keys: in the example, ´ then ¨ then u types ǘ. While ´ then ¨ waits, the text shows ´¨, the chained key’s default identity.

A space is not a valid compose input: what a dead key types with the space bar is its standalone.

Transforms

Transforms rewrite the text as the user types, beyond dead keys. They are LDML transform rules, written as they would be in LDML XML. Here, two hyphens become an en dash, and a third turns that into an em dash:

transforms:
  - - from: '--'
      to: '–'
    - from: '–-'
      to: '—'

transforms is a list of groups, and each group a list of rules. After every key, each group in turn looks at the text before the cursor, and the first of its rules whose from matches the end of that text replaces the match with to. Each group sees what the groups before it wrote, and the dead-key groups that kbdgen generates come first.

from is a pattern in LDML’s syntax: [aeiou] matches one of those characters, ( ) captures text for $1 in to, ^ matches the start of the text, and $[name] matches any member of a set variable. Variables are defined under variables, as strings, sets or usets. This Skolt Sami layout turns an apostrophe typed after a consonant into the softening mark ʹ:

variables:
  sets:
    consonant: b c č d đ f g ǧ ǥ h j k ǩ l m n ŋ p r s š t v z ž ʒ ǯ
transforms:
  - - from: ($[consonant])'
      to: $1ʹ
backspace:
  - - from: ʹ
      to: "'"

backspace holds rules of the same kind for the Backspace key. Here Backspace after ʹ turns it back into an apostrophe. Where no backspace rule matches, Backspace deletes as usual.

A group may also be a reorder group, for scripts whose characters are typed in a different order than they are stored. The rule syntax is in the LDML specification, under transforms.

Transforms run in kbdgen’s keyboard engine: on ChromeOS, and on Windows through the Divvun text service. A macOS .keylayout or a Windows layout DLL can only express transforms that continue a dead key; when kbdgen builds them, it reports the transforms they cannot express.

Long press

On touch keyboards, holding a key offers alternatives. longPress lists them for every key that types the given text, separated by spaces:

longPress:
  a: å æ ä à â ã
  A: Å Æ Ä À Â Ã
  o: ø ö ó ò ô õ
  O: Ø Ö Ó Ò Ô Õ
  z: ʒ ǯ
  Z: Ʒ Ǯ

Candidates use the token syntax of rows, so \u{…} works in them. To choose a default candidate (longPressDefault), or for keys that cycle through characters when tapped repeatedly, use explicit keys (Explicit keys).

bottomRow

host (the default): the app draws the bottom row, with the symbols, globe, space and return keys, so your rows leave it out. authored: you write the bottom row yourself.

Flicks

On tablets, a key can type something else when swiped. Give a layer as rows and flicks; each flick direction (n, ne, e, se, s, sw, w, nw) has rows of the same shape, and the token at each position is what a flick of that key types:

      tablet:
        layers:
          base:
            rows: |
              \s{"`":0.75} á š e r t y u i o p ŋ \s{backspace:1.25}
              \s{shift} a s d f g h j k l đ ŧ \s{shift}
              \s{spacer:0.5} ž z č c v b n m , . \s{spacer:0.5} \s{return:2}
            flicks:
              s: |
                \s{"@":0.75} 1 2 3 4 5 6 7 8 9 0 å \s{backspace:1.25}
                \s{shift} % # € & * ( ) ' " ø æ \s{shift}
                \s{spacer:0.5} q w x - = / ; : ! ? \s{spacer:0.5} \s{return:2}

A flick row must repeat the role keys of its main row; \u{0} or a gap means no flick for that key. Swiping á down types 1.

Explicit keys

For anything rows cannot say, define keys under keys with LDML’s key attributes (output, longPress, longPressDefault, multiTap, flick, width, layer, gap, stretch) and place them with \k{…}. Lists of keys are space-separated key ids. Here, tapping the key twice types ŋ instead of n, and displays labels its keycap:

keys:
  eng: {output: ŋ}
  n-or-eng: {output: n, multiTap: eng}
displays:
  - {keyId: n-or-eng, display: n ŋ}

The key is placed with \k{n-or-eng} in a row. displays can also label keys by output: {output: å, display: Å}. Keys that type only combining marks get a dotted-circle label (◌́) without one.

Normalization

Many accented letters can be written in two ways in Unicode: precomposed (á, U+00E1) or as a letter and a combining accent (a + U+0301). They look the same and are canonically equivalent.

By default, normalization: disabled, the keyboard types exactly the code points you wrote, and transforms match exactly those. This is what macOS does, and what most layouts want.

normalization: enabled

With normalization: enabled, LDML’s default, transforms match text regardless of how it is composed, and the platform chooses whether output is precomposed or decomposed. Turn it on only when your transforms must match text that did not come from your own keyboard. A macOS .keylayout cannot express it, and kbdgen warns when it builds one.

LDML Keyboard 3.0

For each host, kbdgen turns a format 4 layout into an LDML Keyboard 3.0 document, and builds its keyboard from that document. The parts of a layout map to LDML like this:

longPressKeyIds of the keys

Tests and explicit keys refer to keys by id. The ids kbdgen generates follow a pattern:

  • u-00E1 for a key typing á: u- and its code points in hexadecimal;

  • a for a key typing a: a single letter a–z or A–Z, or a digit, keeps its own name when the key has nothing else, such as long-press candidates, flicks or a width (otherwise it is u-0061);

  • space for the space bar, and dk-dk_00B4 for the dead key ´.

Import

kbdgen ldml import -b sme.kbdgen keyboards/mt.xml

This reads LDML keyboard files, CLDR’s included, and writes one format 4 layout per language tag, merging the files of different hosts for one tag. It will not replace an existing layout unless you pass --force. Import reports the comments it dropped, and warns when part of a keyboard can only be written in LDML’s own terms rather than as rows and dead keys.

Using an LDML file as it is

A layout can also point to an LDML file instead of describing the keyboard itself. The path is relative to the layout file:

format: 4
displayNames:
  mt: Malti
  en: Maltese
ldml: ../ldml/mt.xml
targets:
  windows:
    locale: mt-MT

The file then defines the keyboard for every host; ldml: {windows: ../ldml/mt-windows.xml, default: ../ldml/mt.xml} gives one file per host, with default for the rest. Besides format and ldml, such a layout may only have displayNames, decimal, keyNames and targets, and its targets.windows may not set shiftLock, lrmRlm or keyNames: those come from the LDML file. This is also the way for several layouts to share tables, through LDML’s import.

Format 3 layouts

A layout file without a format field is in format 3. The iOS and Android targets build only this format, and many existing bundles use it. The desktop targets build both formats (Which targets build which format). This chapter is a reference for reading and maintaining format 3 layouts; Moving to format 4 shows how to convert them to format 4.

Format 3 is lenient where format 4 is strict: kbdgen ignores fields it does not know, so a misspelt field or section, such as macos for macOS, is silently left out of the build. It does check that required fields are there, that layer names are known, and that text is text: an unquoted number where text belongs is an error.

Dead keys and transforms

Two fields make a dead key:

  • transforms, at the top of the file, maps each dead key’s character to its table: the next key’s character, and what the two together type. The entry ' ' (a quoted space) is what the dead key types on its own.

  • deadKeys, in a platform section, lists for each layer the keys that are dead there. A key not listed types its character normally.

In the windows example above, ´ is dead in default and caps, ¨ in alt and ˇ in alt+shift, and the transforms of Structure say what they do. The windows, macOS, chromeOS and iOS sections have deadKeys. Android has none: on Android, every key whose character is a key of transforms is a dead key, on every layer.

The ' ' entry is required in some places:

  • Windows needs it for every dead key that occurs in its layers.

  • macOS needs it for every entry of transforms once any of its layers has a deadKeys list.

  • iOS and Android do not need it.

There it must be a plain string. Without it the build stops with an error naming the dead key, such as the escape transform ` ` not found for dead key `´` on macOS or kbdse-FI: dead-key state "´" has no standalone (" ") output on Windows.

An entry’s value may itself be a table, which chains a second dead key:

transforms:
  ´:
    ' ': ´
    a: á
    ¨:
      ' ': ´¨
      u: ǘ

Here ´ then ¨ then u types ǘ. Only the Windows and ChromeOS targets support chains. The macOS and iOS targets stop with an internal error on a layout with a chain and a section for them; the Android target stops on a chain in any layout of the bundle.

Write dead-key characters themselves, not \u{…} escapes, in layers, deadKeys and transforms: an escaped entry does not match the key on Windows. Quote keys that YAML would read otherwise, as in format 4 (Quoting in YAML): '0': °, '~', 'n': ŋ.

Escapes

\u{H}, with 1 to 6 hexadecimal digits, stands for the character U+H. Keys that type a space or another invisible character must use it, because spaces separate keys: \u{20}, \u{A0}. Where it is decoded depends on the platform:

  • Windows decodes it in layers, but not in deadKeys or transforms.

  • macOS decodes it in everything it writes, transform results included.

  • ChromeOS decodes it everywhere, as format 4 does.

  • iOS and Android pass the text to the apps as it is written.

\u without braces, as in linnjá\u00ADmolsun, is not an escape in format 3; it stays as written. Use \u{AD}.

Moving to format 4

kbdgen ldml migrate converts a bundle’s format 3 layouts to format 4, in place. It keeps what each platform typed wherever format 4 can say it, and reports every difference it cannot avoid.

Remember that the iOS and Android targets do not build format 4 layouts (Which targets build which format): migrate only bundles that you do not build for them.

  1. Commit your work. The migrator rewrites each file under its own name and keeps no backup; version control is the backup.

  2. See what would happen, without writing anything:

    kbdgen ldml migrate -b sme.kbdgen --dry-run

  3. Fix what blocks (see below), and run it for real:

    kbdgen ldml migrate -b sme.kbdgen

  4. Review the report, then compile and test the result (Checking a layout, Testing layouts).

--report migrate.yaml writes the report to a YAML file instead, and prints only the summary.

What changes

  • Each platform section becomes a variant: windows, macOS and chromeOS under hardware, iOS and android under touch. Each variant is written in full; you may then merge equal parts into a default variant with inherits (Platforms and variants).

  • Layer names become modifier sets: default → none, caps+shift → caps shift, cmd+alt → cmd alt. alt becomes altR on Windows and ChromeOS (AltGr) and stays alt on macOS.

  • Desktop layers are split into rows of 13, 12, 12 and 11 keys.

  • iOS platforms become the sizes phone, tablet and tablet-large; Android’s become phone and tablet. default becomes base, and iPad alt layers become flicks to the south.

  • transforms become deadKeys: the ' ' entry becomes standalone, the other entries compose, and chains nested nodes. Keys that a platform made dead become \d{…} tokens.

  • longpress becomes longPress, each config moves to targets, and macOS space becomes the variant’s space.

  • Comments are lost: the migrator writes the file anew.

Then it loads each new layout and types on it with kbdgen’s engine: every key of every layer except the Caps Lock and shortcut layers, and every dead key with every key it combines with. Each result must match what the format 3 platform typed, or be explained by a reported defect. If not, that is a bug in the migrator, reported as M99, and the layout is not written.

Testing layouts

A bundle can carry typing tests: files in tests/ that press keys on a layout and say what should come out. kbdgen runs them on its keyboard engine, the same engine that types on ChromeOS and in the Divvun text service on Windows, so you can check a layout on any computer before building it.

kbdgen ldml test -b sme.kbdgen

This runs every tests/*.yaml of the bundle, in the order of their file names. Loading a bundle for anything else ignores tests/.

Commits the text, as when the user switches to another window: a pending dead key types its standalone output.

reset

Drops a pending dead key without typing it.

context: text

Replaces the text before the cursor, keeping any pending dead key.

expect: {…}

Checks the result so far (see below).

key is a position name of Rows and key positions (E00 to E12, D01 to D12, C01 to C12, B00 to B11), space, or a scan code in hexadecimal, such as '0x01' for Esc.

mods lists modifiers separated by spaces: shift, caps, ctrl, alt, cmd, extra1, extra2, extra3, and the one-sided shiftL, shiftR, ctrlL, ctrlR, altL and altR. shift, ctrl and alt are the left keys. altgr is the right Alt key acting as AltGr, as on Windows.

A gesture is tap (the default), {longPress: 2} for the second long-press candidate, {multiTap: 2} for the second tap, or {flick: s} for a swipe south; flick directions are n, ne, e, se, s, sw, w and nw, and several separated by spaces make one swipe.

Checking results

expect checks one or more of:

text

All of the text before the cursor, including the context it started from.

preedit

What a pending dead key shows, marked as unfinished: its standalone output, or '' when nothing is pending.

pass

Whether the engine let the last key through to the application unchanged. That is true for shortcuts, for keys of the app’s own such as touch Shift and Backspace keys, and, with the default backspace option, for Backspace with no dead key pending.

layer

The touch layer that the last key switched to, or null for none.

Texts are compared exactly, character by character, with no normalization. They may use \u{…} escapes, which kbdgen decodes: write them in single quotes, '\u{A0}', or with the backslash doubled in double quotes, "\\u{A0}". Quote any text YAML would read otherwise, as in layouts (Quoting in YAML).

Windows

kbdgen target … windows builds a Windows keyboard layout DLL for every layout that has a Windows keyboard. Each layout gets a DLL for each of four architectures: x86, x64, arm64, and the "WOW64" build that 32-bit programs load on 64-bit Windows. kbdgen generates a small Rust crate per layout and builds it with cargo and the rust-lld linker that comes with Rust, so the build runs on Windows, macOS or Linux. You do not need Visual Studio, the Windows SDK or any other Microsoft tool.

Each DLL also carries the layout’s compiled keyboard. The Divvun text service (see The text service) runs that keyboard on Windows and types what a layout DLL cannot, such as long dead-key outputs and transforms.

Prerequisites

  • Rust 1.85 or later, installed with rustup. The toolchain must ship rust-lld, which rustup toolchains do.

  • The standard libraries of the three Windows targets:

    rustup target add i686-pc-windows-msvc x86_64-pc-windows-msvc aarch64-pc-windows-msvc

cargo and rustc must be on PATH. Before building, kbdgen checks all of this and stops with a message naming what is missing:

Error: the Rust standard library is missing for i686-pc-windows-msvc, aarch64-pc-windows-msvc; install it with `rustup target add i686-pc-windows-msvc aarch64-pc-windows-msvc`
Error: `rustc 1.83.0 (90b35a623 2024-11-26)` is too old to build layout crates, which use edition 2024; Rust 1.85 or later is required (`rustup update`)

To build with a particular toolchain, set RUSTUP_TOOLCHAIN or a rustup override for the output directory; the check and the builds both use it.

Building

kbdgen target -b sme.kbdgen -o windows-out windows

-b and -o are required, and come before windows. kbdgen loads the whole bundle, generates one crate per layout, then builds each crate four times and checks each DLL it builds. Nothing is written if any layout has a fatal error.

The build ignores RUSTFLAGS, CARGO_ENCODED_RUSTFLAGS, CARGO_BUILD_RUSTFLAGS, CARGO_BUILD_TARGET, and the CARGO_TARGET_* and CARGO_PROFILE_* variables in your environment, since they would change how the DLLs are linked.

The Windows options:

  • targets.windows.id - names the DLL: kbd followed by the id, here kbdsme. Without an id the name is kbd followed by the first five characters of the language tag (kbdse-FI). See Names and languages.

  • targets.windows.locale - the locale name stored in the DLL (string 1200). Without it, kbdgen uses the language tag. It does not change the DLL’s LCID, which always comes from the language tag.

  • targets.windows.shiftLock - Caps Lock works as Shift Lock: Caps Lock turns it on and Shift turns it off.

  • targets.windows.lrmRlm - Left Shift+Backspace types the left-to-right mark (U+200E) and Right Shift+Backspace the right-to-left mark (U+200F).

  • targets.windows.keyNames - replaces the names Windows gives keys, as programs read them with GetKeyNameText. Any other name fails loading:

    …/layouts/sme.yaml: targets.windows.keyNames.CapsLock: CapsLock is not a Windows key name

  • deadKeys.<identity>.name - the dead key’s name, which GetKeyNameText returns for a key whose unshifted output is that dead key. Only top-level dead keys have names.

  • extraModifiers - up to three more modifier keys, chosen from rightCtrl, capsLock and B00 (the key left of Z on ISO keyboards). The first selects the extra1 layers, the second extra2 and the third extra3. A capsLock used this way no longer toggles Caps Lock. With B00 as a modifier, every layer must have \u{0} at B00.

  • form: abnt2 - adds the 49th key, B11, the key left of Right Shift on Brazilian ABNT2 keyboards, as a twelfth key in the last row. With the default iso form the DLL has no B11.

  • decimal - the character the keypad’s decimal key types. Only the first character is used; without decimal the key types ..

Keys the DLL has no place for are dropped with a warning: keys of a form outside the 49 ISO positions (such as the jis key 7D), and any space bar output other than U+0020.

If the conversion is blocked, the DLL is built without a compiled keyboard, the text service does nothing for that layout, and kbdgen warns:

WARN kbdse-FI: v3 layout: its migration is blocked by defects M05; no engine model is embedded, so the text service stays inert for this layout

kbdgen ldml migrate --dry-run -b <bundle> lists the defects. A blocking defect anywhere in the file blocks the conversion, even outside the windows section: in this example, a macOS layer with 47 keys. The converted keyboard can also type otherwise than the v3 DLL tables; migrate reports where as M09 defects.

Names and languages

Each layout’s keyboard name names its crate, its DLL and its resources. Without an id it is kbd and the first five characters of the language tag, so long tags are cut short (sjd-Cyrl-RU gives kbdsjd-C). The name must start with an ASCII letter and contain only ASCII letters, digits, - and _. Two layouts with the same name are a fatal error:

Error: two Windows layouts are named kbdsme; set the Windows id to tell them apart

divvun-actions also derives the keyboard’s product code from this name (see Installing), so changing the id changes the DLL’s file name and makes it a different keyboard to Windows.

The layout’s display name, the DLL’s description and its language name are all the layout’s displayNames entry for its primary language subtag (se for se-FI). The DLL’s LCID, the language of its strings, comes from the language tag alone. For a tag kbdgen has no LCID for, it is 0x2000, and the default locale name is <language>-<script>-<region>, with Latn and 001 when the tag has no script or region.

Diagnostics

kbdgen reports every problem with a layout’s DLL as it generates it. Each message starts with the keyboard name. There are three kinds:

  • Errors stop the build. An error in any layout stops it before any crate is written. The message names the layout and what is wrong:

    Error: Windows layout for se-FI

Caused by:
    kbdse-FI: layer default has 47 keys, expected at least 48

  • Warnings (WARN) mean the DLL types something other than the layout says, or drops something. The DLL is still built.

  • Information (INFO), once per v4 layout, says what users get only through the text service.

What a layout DLL cannot express

A layout DLL is a set of tables that Windows looks keys up in. It cannot express:

  • dead-key outputs longer than one UTF-16 unit, such as b with a combining acute accent, or a character outside the Basic Multilingual Plane

  • transforms that rewrite text already typed, reorder rules, and backspace rules

  • outputs that mix text and dead keys

  • normalization

  • a key output longer than 16 UTF-16 units

  • a key that both has its own Caps Lock output and is a dead key

  • a space bar that types anything but a plain space

The Divvun text service does all of these, so where it is installed users get the whole layout. The DLL is what users type with where the text service does not run: at the Windows sign-in screen and on the secure desktop, in some games, on machines without the text service, and wherever the text service cannot load the keyboard (see Collecting a diagnostic trace).

For a v4 layout kbdgen sums this up in one message, with counts and up to ten examples of each kind. For the acceptance-test layout in crates/kbd-tsf/tests/acceptance/fixture.kbdgen:

INFO kbdtsfa: without the text service, for example at the sign-in screen, users do not get: 7 transform rule(s) that do not start with a marker (e.g. group 3 rule 1: q'; group 3 rule 2: z'; group 3 rule 3: 𝕫'; group 3 rule 4: sch'; group 3 rule 5: ([…])-; group 3 rule 6: á'; group 4 rule 1: aʠ); 7 dead-key output(s) of more than one UTF-16 unit (e.g. ´ e → ẹ́; ´ z → 𝕫́; ´ b → b́; ´ B → B́; ~ ´ ˇ o → ṍ̌; ~ ´ ˇ space → ~´ˇ; ~ ´ space → ~´)

When the DLL covers everything, the message is:

INFO kbdsme: the layout DLL reproduces the whole keyboard; the text service adds nothing

v3 layouts get the warnings below, but not this summary.

One difference has no warning: on a letter key with Caps Lock on, Shift gives the lowercase letter in the DLL, as in Windows' own layouts. The text service types the layout’s caps shift layer, which impliedLayers: macOS makes uppercase, as on macOS.

Common warnings

A dead-key composition the DLL cannot hold is left out:

WARN kbdse-FI: dead-key input "ˇ -> J" -> output "J\\u{30C}": the output must be exactly one UTF-16 unit outside 0xF000-0xF002; omitted

In the DLL, ˇ then J types ˇJ, as for any key the dead key has no composition for. The text service types J̌. If the DLL matters for this composition, use a precomposed character where Unicode has one.

A key that is a dead key without Caps Lock, and has its own Caps Lock output, different from both its unshifted and its shifted output, cannot have both in the DLL:

WARN kbdtsfa: key E12: SGCAPS cannot be combined with a dead key on the same key; the caps layers are ignored

In the DLL, Caps Lock on that key behaves as if the layout had no Caps Lock layer for it.

A chained dead key (a dead key typed after another) needs a single character that Windows types when the next key does not compose with it. That is its standalone output. When the standalone is longer, kbdgen uses a character from the Private Use Area instead:

WARN kbdtsfa: chained dead-key state "~ -> ´": its standalone output cannot serve as its dead id; using U+F8FF, which an unmatched key emits

Give the nested dead key a one-character standalone to avoid this. A chained dead key none of whose compositions fit the DLL is left out:

WARN kbdtsfa: chained dead-key state "~ -> ´ -> ˇ": none of its children fit the tables; omitted

Space bar outputs other than U+0020 are dropped, as are keys outside the 49 ISO positions:

WARN kbdtsfa: space bar in layer caps: the DLL's space row always types U+0020, so its output "\u{a0}" is dropped

Other warnings name the key and layer, and say what the DLL does instead.

The text service

The Divvun text service is a Windows Text Services Framework (TSF) input method that every Divvun keyboard shares. It runs kbdgen’s keyboard engine on the compiled keyboard in each layout DLL, so it types everything the layout says: dead-key and transform output of any length, chains of dead keys of any depth, rules on text already typed, and outputs of any length, emoji included. While a dead key is pending, it shows the pending text underlined with dots, in programs that let it read their text.

When the text service is installed, users see one entry for each keyboard in Windows' input list, and that entry is the text service. The layout DLL stays installed, as the fallback described above.

Building the text service

Keyboard builds do not build the text service: it is released and installed on its own, and one installation serves every keyboard. divvun-actions builds its installer from the kbdgen repository. Builds of main replace the kbd-tsf-dev-latest prerelease of divvun/kbdgen, a kbd-tsf-v<version> tag gets its own release, and keyboard builds embed the installer of kbd-tsf-dev-latest.

To build it yourself, run kbdgen tsf in a checkout of kbdgen:

kbdgen tsf -w <kbdgen checkout> -o tsf-out

  • -w, --workspace - the kbdgen workspace, which holds crates/kbd-tsf

  • -o, --output-path - the directory to write the DLLs to

Unlike a layout DLL, the text service uses Rust’s standard library, which needs Microsoft’s linker and libraries. Build it on Windows, with the Visual Studio Build Tools (C++), the Windows SDK and the three Rust targets above. On other systems cargo stops with:

error: linker `link.exe` not found

kbdgen tsf writes four files, only once all four have passed its checks:

  • divvun_tip_x86.dll - for 32-bit programs

  • divvun_tip_x64.dll - for x64 programs, also on Arm64 Windows

  • divvun_tip_arm64.dll - for Arm64 programs

  • divvun_tip.dll - for Arm64 Windows: a forwarder that loads the arm64 or the x64 DLL, depending on the program

It prints each file’s absolute path on its own line to stdout, and its log to stderr. The files are unsigned; the release pipeline signs them.

Installing

kbdgen does not install anything. The keyboard installer that divvun-actions builds:

  • runs the text service’s installer first, which installs it into %ProgramFiles%\Divvun\Text Service\<version> and never replaces a newer one. If that fails, the keyboard is installed without it.

  • copies the layout DLLs to System32 and SysWOW64 as the table in What is generated shows

  • registers the layout with kbdi, which also registers a text service profile for it and enables that for the user. The profile’s GUID is the layout’s product code, which divvun-actions derives from the keyboard name.

The text service finds a keyboard’s data through the layout registered under HKLM\SYSTEM\CurrentControlSet\Control\Keyboard Layouts whose Layout Product Code is the profile’s GUID. It reads the compiled keyboard from the DLL that the key’s Layout File names in System32.

Uninstalling the last Divvun keyboard also removes the text service.

Collecting a diagnostic trace

The text service never records typed text, the text around the caret, or which keys were pressed. It reports what it does as Windows events (ETW) from the provider Divvun.Keyboard.TextService, whose GUID is {B7732613-C499-504F-2AB7-FF5A4E513A9B}. Windows keeps these events only while a trace session is collecting them, and only an administrator can start one.

To collect a trace on a user’s machine, open an elevated Command Prompt and start a session:

logman start divvun-tsf -p {B7732613-C499-504F-2AB7-FF5A4E513A9B} 0xffffffffffffffff 5 -o %TEMP%\divvun-tsf.etl -ets

Reproduce the problem, then stop the session and decode the trace:

logman stop divvun-tsf -ets
tracerpt %TEMP%\divvun-tsf.etl -o %TEMP%\divvun-tsf.xml -of XML -y

macOS

The macOS target writes a keyboard-layout bundle: one Apple .keylayout file per layout, an icon for each layout, and the names macOS shows in its list of input sources. macos build also wraps the bundle in an installer package that puts it in /Library/Keyboard Layouts.

A .keylayout is a static description of key maps and dead keys; there is no Input Method behind it. Whatever a layout needs beyond that is lost on macOS, and for v4 layouts kbdgen warns about each such feature (see Warnings and errors).

Prerequisites

  • kbdgen. macos generate runs on any operating system.

  • On macOS, to convert icons: ImageMagick’s convert (brew install imagemagick) and iconutil, which ships with macOS. Neither is needed when resources/macos has no icons.

  • To build the installer: pkgbuild and productbuild, which ship with macOS.

On other operating systems the bundle is written without icons (with a warning for each one skipped), and macos build leaves out the installer with a warning. macos installer is not checked in advance: it fails because pkgbuild cannot be started.

Layouts

The layout formats have chapters of their own; this section covers what the macOS target does with them. A bundle may mix v3 and v4 layouts; both are written into the one macOS bundle, in the order of their language tags. A layout without macOS layers is skipped silently: a v3 layout without a macOS section, or a v4 layout with neither a hardware.macOS nor a hardware.default variant.

Each layout’s keyboard name is its language tag with - and _ removed: se-NO becomes seNO. It names the .keylayout and .icns files and the layout’s KLInfo_ entry in Info.plist, and ends its input source ID. Two layouts with the same keyboard name are an error. The keyboard’s numeric id in the .keylayout is derived from the name.

Layers

primary.layers maps layer names to key strings. Each string is split on whitespace, line breaks included, and the tokens fill the 48 ISO positions in order: E00–E12 (the number row, starting left of 1), D01–D12, C01–C12, then B00–B10 (B00 is the ISO key left of Z). How the tokens are spread over lines does not matter. A layer with fewer than 48 tokens is an error; tokens after the 48th are ignored.

The first layer in the file is the default key map, used when no other one matches, whatever its name; list default first.

The typing layers also match with Command held (command?). If macOS takes the first key map that matches, Command shortcuts use those layers and a later cmd layer is never reached. This is an open question in the spec; kbdgen keeps these terms as they have always been.

Token rules:

  • \u{…} escapes are decoded in every output kbdgen writes.

  • \u{0} is not "no key" here: it is written as the output U+0000.

  • The space bar types a space (U+0020) in every layer. macOS.space is read but ignored. A v4 layout can put other characters on the space bar.

  • The keypad’s decimal key types the layout’s top-level decimal, or . when there is none.

  • Return, Tab, Delete, Escape, the arrows, the function keys and the rest of the keypad are fixed by kbdgen and the same in every layer.

Dead keys

Dead keys need both macOS.deadKeys and the layout’s top-level transforms:

  • deadKeys lists, per layer, the tokens that are dead keys on it.

  • Each top-level transforms key is a dead key, mapping the token typed next to the result. Its ' ' entry is the dead key’s standalone output: what it types when followed by a key with no composition, or by the space bar. Every top-level transform needs a ' ' entry, and it must be a string; otherwise building the layout fails.

  • Compositions apply on every layer that has a deadKeys entry, and only there. A key on a layer without one, pressed after a dead key, types the dead key’s standalone output and then its own.

  • One level only: a composition whose value is itself a mapping makes kbdgen abort (nested transforms under … are not supported on macOS).

  • A token listed in deadKeys with no transform of its own is an error.

  • A layout with transforms but no macOS.deadKeys, or the other way round, builds without dead keys and logs a warning.

  • Put a dead key on a layer only once. When the same dead-key token is at two positions of one layer, only the last position works.

v4 layouts

A v4 layout (format: 4) gets a .keylayout when it has a hardware.macOS variant, or failing that a hardware.default one. kbdgen compiles the layout and adapts the macOS keyboard to the .keylayout format:

  • Each hardware layer becomes a key map. Its modifier sets give the <modifier> terms; a layer read from v3 gets the term v3 gave it. The other layer, if there is one, is the default key map; otherwise the first layer is.

  • The keys are the 48 ISO positions and the space bar. The space bar follows the layout, so space: entries work: vro.yaml has space: {caps: '\u{A0}'}, and its Caps Lock map writes <key code="49" output="&#x00A0;" />.

  • The keypad’s decimal key types the layout’s decimal, or ..

  • The deadKeys table becomes dead-key states. kbdgen runs the keyboard engine on each dead key and every key value to find what the .keylayout must type, so chained dead keys (a dead key that composes with another dead key) work.

  • The display names are the layout’s displayNames.

What a .keylayout cannot express is left out, with one warning per layout and feature:

  • transforms that do not start with a dead key, reorder groups, and custom backspace rules;

  • outputs mixing text and dead-key markers;

  • dead-key results that leave text and a marker, or several markers;

  • long-press, multi-tap and flick gestures;

  • key displays other than the automatic ones, and keyNames labels;

  • extra modifiers and other Windows-only options;

  • normalization: enabled.

A layout that loses nothing gets one information message instead: the .keylayout expresses every feature of the keyboard.

The exhaustive rules are in docs/spec/ldml/macos.md.

Migrating a v3 layout

After kbdgen ldml migrate, a layout’s .keylayout is the same as before, except where v3 behaved oddly. kbdgen’s tests compare the two documents for its test layouts, and allow only these differences:

  • \u{0} becomes no key, where v3 typed U+0000.

  • The space bar follows the old macOS.space entries and composes with dead keys, where v3 always typed a plain space.

  • Dead keys compose on every layer, not only on layers listed in macOS.deadKeys.

  • A dead key pressed after another dead key types their composition when the transforms define one, where v3 typed the first dead key’s standalone output and started the second.

  • A transform whose dead key is on no macOS layer gets no dead-key state; it could not be reached anyway.

  • The ctrl and cmd layers come after the others in the file, which changes nothing when typing.

Each line of a layer is a row and each whitespace-separated token a key. A token of the form \s{id} or \s{id:width} is a special key, and \s{"x":width} is a key typing x with a custom width. Long press, dead keys and transforms

  • longpress (top level) maps a key to its long-press alternatives, separated by spaces.

  • iOS.deadKeys maps layer names (default, shift, …) to the keys that are dead keys on them. It is passed to the app as it is, for all three device sizes.

  • transforms (top level) gives the dead keys' compositions, as for the other targets. Every top-level transform is passed to the app, whether its dead key is on an iOS layer or not. Only one level is supported: a composition whose value is itself a mapping makes kbdgen abort. A top-level transform that is a string is passed as empty, with a warning.

print-pkg-ids

init

Registers the app with App Store Connect, once per app, before the first build. It needs targets/ios.yaml and an en entry in the locales of project.yaml, whose name is the app’s name. In the output directory, it runs:

  1. fastlane produce -a <packageId> --app_name <name>, creating the app;

  2. fastlane produce group -g group.<packageId> -n "<name> Group", creating the app group;

  3. for every keyboard identifier, fastlane produce -a <id> --app_name "<name>: <folder>" --skip_itc, creating its App ID;

  4. for every identifier, the app’s included, fastlane produce enable_services -a <id> --app-group and fastlane produce associate_group -a <id> group.<packageId>.

The per-identifier commands run in parallel. A failing command stops init with an error that quotes the end of fastlane’s output.

build

Runs these steps, stopping at the first that fails:

  1. Clone: git clone https://github.com/divvun/giellakbd-ios.git repo in the output directory. Use an empty output directory: the clone fails when repo already exists.

  2. Keyboard definitions: writes repo/Keyboard/Models/KeyboardDefinitions.json.

  3. Xcode project: adds a keyboard target per layout, and writes the plists, app names and icons.

  4. Provisioning: for every bundle identifier, runs fastlane match appstore and fastlane sigh, at most twelve at a time, then records each provisioning profile in the Xcode project and in repo/opts.plist.

  5. Pods: pod install --repo-update in repo.

  6. Archive: xcodebuild archive of scheme HostingApp (Release, any iOS device) into <packageId>.xcarchive, its log shown through xcbeautify, then xcodebuild -exportArchive into ipa.

The output of pod and xcodebuild goes to the terminal; when one fails, its log is above the error. git, fastlane and security run quietly, and a failure quotes the end of their error output.

Android

kbdgen builds an Android keyboard app from giellakbd-android, a keyboard app based on the Android Open Source Project keyboard. kbdgen target android build clones the app, downloads its native libraries, writes a keyboard into it for every layout with an android section, and runs Gradle to build a release APK. One app holds all of the bundle’s Android layouts.

kbdgen target -b sme.kbdgen -o android-out android build

Prerequisites

  • git and tar on PATH.

  • Network access to GitHub: the build clones the app and asks the GitHub API, without authentication, for the native libraries' latest releases. GitHub limits how often an address may do that.

  • The Android SDK, found through ANDROID_HOME or sdk.dir in repo/local.properties, and a JDK that the app’s Gradle build accepts; giellakbd-android asks for JDK 17 or newer. Gradle itself comes with the app.

  • ImageMagick’s convert, but only when the bundle has an Android icon (see Icon).

Commands

All three take the bundle and the output directory before android, as in the example above.

Clones the app as clone does, downloads the native libraries, then generates as generate does. Use this.

Clones https://github.com/divvun/giellakbd-android into <output>/repo. If <output>/repo already exists, the clone fails and kbdgen uses the existing checkout as it is: Using the existing checkout at <output>/repo.

The download step, which only build runs, takes libdivvunspell from the newest release of divvunspell that has an android-jnilibs asset, and libpahkat_client from the newest release of pahkat that has an android asset, skipping drafts and prereleases. Names

The layout must have an English display name: kbdgen names the keyboard’s resource files after it, lowercased with every character other than a-z and 0-9 replaced by x, so Northern Sami gives northernxsami. Two layouts whose English names give the same resource name overwrite each other’s files.

The English name is also the keyboard’s name in Android’s list of keyboards. Its names in other languages are added for each language the app has resources for (a res/values-<language> directory), and skipped for the rest. The app’s name, as Android lists it among input methods, is the last layout’s English name followed by Keyboard; in each language of project.yaml locales that the app has resources for, it is that locale’s name.

Platforms and layers

primary is the phone keyboard and tablet-600 the keyboard for screens at least 600dp wide; both are required. Each has a default layer and may have a shift layer; there are no other layers. The symbol, phone and number keyboards, and the bottom row with the symbols key, comma, space, period and return, come from the app.

Each line of a layer is one row of keys, split on whitespace:

  • \s{shift} is the Shift key and \s{backspace} the Backspace key. Other \s{...} tokens are not special keys.

  • Every other token is a key that types the token. kbdgen does not decode \u{...} escapes for Android, so write the characters themselves.

  • The first ten keys of the first row show the digits 1 to 9 and 0 as hints, in order, and type them on a long press.

  • Key widths follow the longest line of the default layer: with n keys in it, each key is 1/n of the keyboard’s width (of 90% of it on tablets), and Shift and Backspace share what is left of their row.

Long press

The top-level longpress section lists, for a key, the keys a long press offers, separated by spaces. Outside the first row, the first of them is also shown on the key as a hint. A key with an empty list stops the build, naming the layout, platform, layer and line.

Dead keys

Every key whose output is a top-level entry of the layout’s transforms is a dead key, on every layer. What it composes is written to the app, in assets/layouts/<tag>.json, only when the layout has an android.config section; without one, its keys are still dead but compose nothing.

Speller

  • spellerPath - the speller file the keyboard uses, such as se.bhfst; required in config

ChromeOS

kbdgen target chromeos writes a ChromeOS input method: a Chrome extension (Manifest V3) with one input method per layout. The extension runs the same keyboard engine as the Windows text service, compiled to WebAssembly, on each layout’s compiled keyboard, so dead keys, transforms and everything else the layout says type on ChromeOS as they do in the engine.

kbdgen target -b sme.kbdgen -o chromeos-out chromeos

Prerequisites

Generating an extension needs only kbdgen: the engine is built into the kbdgen binary. To try the extension you need a ChromeOS device on which you may load unpacked extensions; chrome.input.ime, which the extension runs on, exists only on ChromeOS.

Building kbdgen itself from source needs Rust’s WebAssembly target, because kbdgen’s build compiles the engine for it:

rustup target add wasm32-unknown-unknown

Target configuration

targets/chromeos.yaml is required; without it the build stops with targets/chromeos.yaml is missing. Any scalar is read as a string.

appId: dnihbfekindancgddjehgonciaopmkbe
build: 11
version: 1.0.0

build

yes

The extension version Chrome compares, written to manifest.json as version: one to four dot-separated integers from 0 to 65535, without leading zeros, such as 11 or 1.0.3. Anything else, such as 1.0.3-beta, stops the build.

yes

The version shown to users, written as version_name. Any text.

yes

The extension’s name and description come from locales in project.yaml, which must have an en entry; without one the build stops with project.yaml: locales has no en entry.

Keyboard layouts

Both layout formats work, side by side in one bundle:

  • A v4 layout (format: 4) gets an input method from its chromeOS hardware variant, or from default when it has none. A v4 layout with neither has no input method.

  • A v3 layout gets an input method from its chromeOS section, and a v3 layout without one has none. kbdgen converts the layout in memory, as kbdgen ldml migrate would, without changing the file.

If no layout has a ChromeOS keyboard, the build stops with no layout has a chromeOS keyboard.

If the conversion finds a blocking problem, such as a layer without exactly 48 keys, the build stops and names the layout and the defect codes:

Error: vro: the v3 layout's migration is blocked by defects M05; `kbdgen ldml migrate --dry-run` reports them

Locale and XKB layout

Each input method has two settings, from targets.chromeOS in a v4 layout or from chromeOS.config in a v3 one. Both are optional:

  • locale - the language ChromeOS lists the input method under; en-US by default

  • xkbLayout - the ChromeOS keyboard layout beneath the input method; us by default. Keys the input method lets through, such as Ctrl and Search shortcuts, take their meaning from this layout.

Icon

The extension icon is the default icon of the bundle’s ChromeOS resources: icon.png in resources/chromeos, or in resources/chrome, the name older bundles use. A bundle may have only one of the two directories. kbdgen copies the file to the extension unchanged, and Chrome scales it to 16, 48 and 128 pixels, so use a square PNG of at least 128 by 128 pixels.

  • An icon in any other format, such as icon.svg, stops the build: <path>/icon.svg: a ChromeOS extension icon must be a PNG.

  • Per-layout icons (icon.<tag>.png) are not used: an input method has no icon of its own.

  • Without an icon the extension has none, and kbdgen says The bundle has no ChromeOS icon.png, so the extension has no icon.

Output

The output directory is the unpacked extension:

  • manifest.json - the extension manifest, with one input method per layout

  • background.js - the service worker that runs the engine

  • engine.wasm - the keyboard engine

  • models/<tag>.dvkb - each layout’s compiled keyboard

  • _locales/<language>/messages.json - the names of the extension and of each input method, in en and in every language the layouts have a display name in

  • icon.png - the extension icon, if the bundle has one

kbdgen checks everything before it writes anything, so a failed build leaves the directory as it was. A successful build empties models/ and _locales/ first, and removes an icon.png the bundle no longer has, so nothing of an earlier build remains.

Trying it on a Chromebook

  1. Copy the output directory to the Chromebook.

  2. Open chrome://extensions, turn on Developer mode and choose Load unpacked, then pick the directory.

  3. Add the new input method in the ChromeOS input settings (Settings, Device, Keyboard and inputs, Input on current releases; the path differs between ChromeOS versions). It is listed under the language of its locale.

  4. Switch to it from the input menu in the shelf, or with Ctrl+Space.

After rebuilding, copy the directory again and press the extension’s reload button on chrome://extensions. If a layout cannot load, the service worker logs Divvun keyboard <tag> could not load: <reason>, which shows under the extension’s Errors.

Publishing

Zip the contents of the output directory, with manifest.json at the top of the archive, and upload the zip in the Chrome Web Store developer dashboard. Each upload needs a higher build than the one before.

kbdgen warns, once per layout and kind, about what a layout says that a ChromeOS key event cannot reach. Each warning gives a count and up to ten examples. The layout still builds; only those parts are lost.

  • project.yaml: locales has no en entry

  • targets/chromeos.yaml: build "1.0.3-beta" is not a Chrome extension version: one to four dot-separated integers from 0 to 65535, without leading zeros

  • <tag>: the v3 layout’s migration is blocked by defects …, described under v3 layouts

  • no layout has a chromeOS keyboard

  • <path>/icon.svg: a ChromeOS extension icon must be a PNG

  • <bundle>/resources/chrome and <bundle>/resources/chromeos both hold ChromeOS resources; keep one, when the bundle is loaded

How it types

  • A dead key shows what it would type as a composition, which the next key completes or replaces.

  • Backspace runs the layout’s backspace rules, if it has any. Otherwise it cancels a pending dead key, and with none pending the application deletes as usual.

  • Keys the layout does not handle, such as the arrows, Enter, Tab and shortcuts, go to the application. A pending dead key is typed first, as it is on macOS.

  • In a password field nothing is shown as a composition, and the input method keeps no text from the field.

Limits

  • ChromeOS stops an extension’s service worker when it has been idle for a while. A dead key left pending that long is dropped, and the next key types on its own.

  • Left Alt never types (see v4 layouts), and neither does a key whose position no ChromeOS key event carries.

  • The input method draws no on-screen keyboard: long-press keys, key labels and keyNames are not used.
